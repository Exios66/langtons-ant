# Engineering & Performance Blueprint: Browser Langton's Ant / Turmite Simulator

Research notes for a portfolio-quality interactive Langton's Ant / turmite simulator (unbounded 2D grid, N-color × M-state rules, thousands of steps per frame, multi-ant). Researched October 2026.

## Key Question 1 — Grid representation for an unbounded 2D automaton

### Takeaway
Use a **paged/chunked grid**: `Map<number, Uint8Array>` where each chunk is a 64×64 (4,096-cell) `Uint8Array` keyed by a packed chunk coordinate, with lazy chunk creation and refcount-based eviction. This is the production-proven shape (Golly, the reference CA explorer, stores unbounded universes in tiles with up to 256 states/cell), and it is the only option whose memory is bounded by *touched* cells at ~1 byte/cell. A sparse `Map` of live cells is the correct runner-up only for small exploratory runs; a wrapping torus is the fallback for "screensaver mode" but destroys the unbounded property that makes long runs interesting.

### Cited Findings
- Golly, the de-facto production CA application, "supports bounded and unbounded universes, with cells of up to 256 states" and multiple simulation algorithms including Gosper's hashlife for huge time scales — i.e., unbounded grids are implemented with multi-algorithm, region-based storage rather than one flat array. — [Golly home page](https://golly.sourceforge.io/)
- Golly's unbounded universes also support multiple topologies (plane, torus, Klein bottle) — the topology is a property layered on the storage, not the storage itself. — [Golly README (mirror)](https://github.com/mintpi/golly)
- A production vanilla-JS CA framework (chirs/cellular_automata) uses "typed-array storage, precomputed neighbor indexes, and an allocation-free update loop; a 960×540 Game of Life grid runs at ~140 generations/sec" (~73M cell-updates/s) on the main thread. It supports turmites ("Langton's Ant and multi-color turmites like LLRR and RRLLLRLLLRRR, with up to four ants"). — [chirs/cellular_automata README](https://github.com/chirs/cellular_automata)
- That same framework deliberately keeps grids **toroidal** (bounded, wrapping) because typed-array storage needs a fixed stride; its roadmap lists unbounded/chunked storage and WebGL as future work, confirming chunking is the non-trivial extension. — [chirs/cellular_automata README / ROADMAP](https://github.com/chirs/cellular_automata)
- Golly's QuickLife algorithm is described as "a fast, memory-efficient algorithm" using a conventional (non-hashing) per-cell design while remaining unbounded — production engines separate the *rule* from the *memory layout*. — [Golly Help: QuickLife](https://golly.sourceforge.io/Help/Algorithms/QuickLife.html)
- A high-performance C++ Langton's Ant toolchain (nluka/langant-explorer) stores each cell in 1 byte ("each cell (pixel) occupies 1 byte") with grids up to 65,535², and its state format is rule tables + grid + ant position — evidence that 1 byte/cell is the accepted density for turmite universes. — [nluka/langant-explorer README](https://github.com/nluka/langant-explorer)
- Community microbenchmarks show `Map` random access/iteration is measurably slower than typed-array/sparse-array indexing at scale (the benchmark exists specifically because the gap matters). — [MeasureThat: sparse array vs Map](https://www.measurethat.net/Benchmarks/Show/22496/1/sparse-array-vs-map-for-random-access-and-iteration)
- GC pressure from per-frame allocation is a documented real-world failure mode in JS CA sims: the Teb's Lab Game-of-Life optimization writeup had to eliminate fresh arrays per frame and neighbor-pointer arrays because "this function triggers a lot of garbage collection." — [Teb's Lab: How I optimized Conway's Game of Life](https://medium.com/tebs-lab/optimizing-conways-game-of-life-12f1b7f2f54c)

### Inferences
- **Memory math (single ant, 10⁸ steps).** Each step touches exactly one cell, so distinct visited cells ≤ 10⁸. For the classic RL ant the settled highway is ~2 cells wide, so the real footprint after 10⁸ steps is ~2×10⁸ bytes worst case, realistically on the order of 10⁷–10⁸ cells:
  - Chunked `Uint8Array` (64×64): ≤ 1 B/cell → ≤ 100–200 MB raw cell data + a chunk index of only ~24k–49k Map entries (~1–2 MB) → **~100–200 MB total**. Trivially fits in a browser tab (typical tab heap budget is ≥ 2 GB; ArrayBuffer allocation is outside the JS heap but still limited).
  - Sparse `Map<packedXY, color>`: each Map entry in V8 costs roughly 40–80 bytes (key + value slots in hash-table arrays plus load-factor headroom) → 10⁸ entries ≈ **4–8 GB**. Infeasible; and if cells are stored as `{x,y,color}` objects instead of packed ints, multiply by several more.
  - Fixed torus: constant memory (e.g., 8192² Uint8Array = 64 MB), but a 10⁸-step highway is ~10⁸ cells long; an 8192-cell-wide torus wraps ~12,000 times, so the ant runs over its own road — you lose the iconic unbounded highway. A torus is only acceptable if you also offer periodic *growth* (resize/copy to a bigger array when the ant approaches the edge — cheap for a single ant since a resize+copy of a 64 MB array is ~10s of ms, amortized over millions of steps).
- **Memory math (10⁵ ants × 10⁴ steps = 10⁹ step-events).** Upper bound on distinct cells = 10⁹ → chunked grid worst case ~1 GB (fits, but design for it: lazy chunks + a cap/eviction policy); sparse Map worst case ~40–80 GB (impossible). In practice multi-ant runs co-locate and interact, so footprints are far smaller — but the *engine* must not assume it. Rule of thumb: chunked typed arrays stay viable to ~10⁸–10⁹ live cells; sparse Map caps out around 10⁶–10⁷ live cells.
- **Which structure production libraries use:** chunked/tiled allocation (Golly tiles for unbounded grids; hashlife quadtrees when compression matters) is the production answer. Minecraft-style 64×64 chunks in a `Map` is the same idea; 64×64 = 4,096 cells/chunk keeps chunk count (and Map overhead) low while a chunk still fits in L1/L2 cache (4 KB).
- **Recommended data layout:** chunk key = `(cx & 0xFFFF) << 16 | (cy & 0xFFFF)` packed into one int; coordinates stored as signed 32-bit ints per ant, chunk-local index = `(y & 63) << 6 | (x & 63)`. No allocation in the hot path: lookup chunk once per step, then all touches stay inside the chunk (ant steps move ±1 cell, so ~99% of consecutive steps hit the same chunk — cache the last chunk reference).
- **Eviction:** chunks whose every cell returns to color 0 can be dropped (refcount per chunk from resident ants, or a periodic sweep comparing against zero). This is optional; without it memory grows monotonically with footprint, which for Langton's ant is *actually the correct semantics* (the pattern is permanent).

### Gaps
- No fetched source gives a measured V8 `Map` bytes-per-entry figure; the 40–80 B/entry estimate is an inference from V8's hash-table design and should be validated with Chrome DevTools memory snapshots before quoting it publicly.
- Golly's exact internal tile size for QuickLife (the 16×16-tile "tilecache" in its source) was not confirmed in the fetched help pages; confirm in `golly` source (`LifeAlgo/qlife` sources) if the blueprint cites tile dimensions.

## Key Question 2 — Rendering strategy

### Takeaway
Use a **two-layer Canvas2D pipeline**: (1) an offscreen "world texture" canvas at 1 cell = 1 pixel, updated *incrementally* via `putImageData` with dirty-rect arguments for only the cells changed this frame; (2) the visible canvas, repainted each frame with a single `drawImage(worldTexture, ...)` under a pan/zoom transform with `imageSmoothingEnabled = false`. Never call `fillRect` per cell; never `putImageData` a full-screen buffer every frame. This beats WebGL for 2–16 colors at typical viewport sizes, and `OffscreenCanvas` in a Worker (Baseline since March 2023) is the escalation path if rasterization ever shows up in profiles.

### Cited Findings
- `putImageData` accepts an optional dirty rectangle: "If a dirty rectangle is provided, only the pixels from that rectangle are painted" — incremental updates are a first-class API feature, and the method is Baseline (widely available since July 2015). — [MDN: CanvasRenderingContext2D.putImageData](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/putImageData)
- Measured: a full-frame `putImageData` of a 320×180 buffer takes ~50 µs (20,293 ops/s) on Chrome 133 — i.e., a 4K-sized (3840×2160, 33 MB) full-frame `putImageData` extrapolates linearly to ~1.8 ms per frame, which is 60 fps-budget-eating if done every frame at high DPR. — [MeasureThat: clearing canvas v2](https://www.measurethat.net/Benchmarks/Show/33628/1/clearing-canvas-v2)
- Measured: canvas-to-canvas `drawImage` blits are ~2 orders of magnitude cheaper than `getImageData`+`putImageData` (full-canvas `drawImage` ≈ 1.15M ops/s vs `putImageData` ≈ 16K ops/s in the same benchmark) — so scale/pan by `drawImage` from the offscreen texture, not by re-composing pixels. — [MeasureThat: PutImageData vs DrawImage vs fillRect](https://benchmarklab.azurewebsites.net/Benchmarks/Show/589377)
- Measured: per-pixel `fillRect` is ~30–100× slower than batched ImageData writes (putImageData 411 ops/s vs fillRect 13 ops/s on 320×180 random pixels; fillRect also 1 op/s in the 1000×500 variant) — per-cell `fillRect` is the single worst renderer choice for this workload. — [MeasureThat: drawing pixels putImageData vs fillRect](https://www.measurethat.net/Benchmarks/Show/33591/1/drawing-pixels-putimagedata-vs-fillrect), [MeasureThat: Canvas Pixel vs Fill rect](https://www.measurethat.net/Benchmarks/Show/11760/0/canvas-pixel-vs-fill-rect)
- Conversely a single `fillRect` is a very cheap *clear* (5.1M ops/s vs 20K for putImageData-fill) — use one full-canvas fill for background/erase between blits, not per-cell. — [MeasureThat: clearing canvas v2](https://www.measurethat.net/Benchmarks/Show/33628/1/clearing-canvas-v2)
- The Rust/WASM GoL tutorial converges on the same design: keep the universe in linear memory (a `Uint8Array`) and render "to Canvas directly from memory" — building a String (or recomposing structures) per frame wastes copies; the render loop reads the flat cell buffer straight into pixels. — [Rust and WebAssembly tutorial: Implementing Life / Rendering to Canvas Directly from Memory](https://rustwasm.github.io/book/game-of-life/implementing.html)
- **OffscreenCanvas is Baseline "Widely available" since March 2023** (MDN), usable in Workers, is a transferable object, and has 96.76% global support (caniuse, March 2026); the 2D context on OffscreenCanvas has 96.69% support. So a Worker-owned renderer with `canvas.transferControlToOffscreen()` is a safe default on 2026 browsers, with a main-thread fallback pattern documented by Three.js. — [MDN: OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas), [MDN: OffscreenCanvasRenderingContext2D](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvasRenderingContext2D), [caniuse: OffscreenCanvas](https://caniuse.com/offscreencanvas), [caniuse: OffscreenCanvas 2d context](https://caniuse.com/mdn-api_offscreencanvas_getcontext_2d_context), [Three.js OffscreenCanvas manual](https://threejs.org/manual/pages/offscreencanvas.html)
- Golly needed a second rendering tier ("unbounded zooming... astronomical patterns"; diamond/circular icons at scales 1:8/1:16/1:32) — at extreme zoom-out, rendering one icon per cell-region (minification) is the production answer; your world-texture + `drawImage` with smoothing off gives the same effect for free at integer zoom levels. — [Golly home page](https://golly.sourceforge.io/), [Golly Help: QuickLife](https://golly.sourceforge.io/Help/Algorithms/QuickLife.html)

### Inferences
- **Why dirty-rect wins decisively for this workload:** a single ant changes exactly **one cell per step**. Even at 1M steps/s you change ≤ N_ants × 10⁶ cells/s, but per *frame* (16.7 ms) at, say, 100K steps/frame with 1 ant that's ~1–2 cells per frame in steady highway state. A dirty-rect pipeline makes steady-state rendering cost ~0 µs vs ~1.8 ms full-frame. Switch to the full-frame path only when changed-cell count > ~5% of viewport pixels (multi-ant chaos), at which point recompose the viewport region from chunks into one ImageData and put it once.
- **devicePixelRatio-aware sizing:** set `canvas.width = cssWidth * devicePixelRatio` (cap DPR at 2 to halve fill rate), `canvas.style.width = cssWidth + 'px'`, and apply the pan/zoom as a context transform (`setTransform(zoom*dpr, 0, 0, zoom*dpr, panX*dpr, panY*dpr)`). Render the *viewport only*: compute visible world rect from the inverse transform and decompose only chunks intersecting it.
- **Zoom/pan pattern:** keep `worldX = (screenX - panX) / zoom`; on zoom-at-cursor keep the world point under the cursor fixed (`pan' = screen - world * zoom'`). `imageSmoothingEnabled = false` gives crisp cell edges at integer zoom; for zoom-out below 1×/cell, switch to per-chunk downsample (draw each chunk as a scaled thumbnail, or pick minified palette per 2×/4×/8× levels like Golly's icon scales).
- **When WebGL would win (runner-up):** viewport sizes ≥ ~4K at DPR ≥ 2, dozens of animated overlays (ant sprites, trails, glow), or a GPU-side color LUT. Implementation = one 2D texture holding the grid (upload dirty chunks per frame with `texSubImage2D`), one fragment shader sampling the texture with a palette LUT. It is more code (shader + texture management + fallback) for roughly the same visible result at this app's scale; keep it as a stretch goal, matching the plan of existing JS CA engines that list WebGL as roadmap rather than core. — [chirs/cellular_automata ROADMAP](https://github.com/chirs/cellular_automata)
- **When OffscreenCanvas-in-Worker wins:** if the main thread ever does UI work during animation (React controls, stats DOM updates) and jank appears in profiles; move the world-texture rasterization + putImageData into the worker (sim + render together in one worker is the cleanest: the main thread then only composites nothing — the canvas *is* the worker's). Fallback: feature-detect `transferControlToOffscreen` and run the same loop on the main thread.

### Gaps
- No fetched source provides head-to-head numbers for Canvas2D vs WebGL2 texture-upload rendering of automata; the WebGL recommendation is based on API cost structure and Golly/engine roadmap behavior, and should be validated with a prototype profile if 4K+DPR2 targets matter.
- Exact per-browser cost of `putImageData` dirty-rect subregions (does Chrome cost-scale with dirty area or with buffer size?) was not found in fetched sources; measure with `performance.now()` around calls in the prototype.

## Key Question 3 — Step scheduling: where the time actually goes

### Takeaway
The ant step itself is nearly free (~15–30 ns/step extrapolated from a measured 73M cell-updates/s JS engine) — **time goes to GC pressure, full-frame pixel writes, and rasterization**, not to the rule. Schedule with `requestAnimationFrame` + an adaptive steps-per-frame controller targeting a ~10 ms frame budget, map the speed slider exponentially (1 step/s → 1M steps/s over the slider range), and implement turbo as render-skipping batches that yield every ~30–50 ms. A main-thread loop is sufficient for the entire product; Web Worker + SharedArrayBuffer is not deployable on GitHub Pages without cross-origin-isolation headers and is not worth it here.

### Cited Findings
- Measured engine throughput: 960×540 Game of Life (518,400 cells) at ~140 generations/s in vanilla JS with typed arrays and an allocation-free loop ≈ **73M cell-updates/s ≈ 14 ns per cell-update**. One ant step (1 read + 1 table lookup + 1 write + 1 move) is comparable work → ~1M steps/s consumes <2% of one frame. — [chirs/cellular_automata README + npm run bench](https://github.com/chirs/cellular_automata)
- GC is the documented silent killer: the Teb's Lab optimization case study attributes most early slowness to per-frame allocations ("Every time I computed a frame, I used a brand new array... this triggers a lot of garbage collection") and per-call neighbor arrays; the fix — preallocate, reuse buffers — is exactly the allocation-free loop pattern chirs/cellular_automata credits for its speed. — [Teb's Lab: Optimizing Conway's Game of Life](https://medium.com/tebs-lab/optimizing-conways-game-of-life-12f1b7f2f54c), [chirs/cellular_automata](https://github.com/chirs/cellular_automata)
- Golly markets responsiveness *while generating or garbage collecting* as a key feature — production CA apps treat scheduling/GC-avoidance as a core requirement, not an optimization afterthought. — [Golly home page](https://golly.sourceforge.io/)
- **SharedArrayBuffer requires cross-origin isolation**: Chrome gates SAB behind `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp` (since Chrome 92 on desktop; Firefox similar; Safari 15.2+). Both headers must be served at the document level. — [web.dev: COOP & COEP](https://web.dev/articles/coop-coep), [Chrome blink-dev announcement](https://groups.google.com/a/chromium.org/g/blink-dev/c/_0MEXs6TJhg/m/F0UduPfpAQAJ)
- Cross-origin isolation also buys higher-resolution timers: `performance.now()` precision improves from ~100 µs to ~5 µs when isolated — relevant only if you build adaptive frame controllers on sub-frame timing. — [web.dev: COOP & COEP](https://web.dev/articles/coop-coep)
- Existing JS turmite sims expose exactly the scheduling UX this blueprint implies: langtonant.com offers "Steps per Refresh: 1 … 500,000" and refresh delays from 1 ms to 5 s, on grids up to 5000×5000 — i.e., step-batching per frame is the standard speed control, not per-step timers. — [langtonant.com](http://www.langtonant.com/)
- Simpler existing apps that step on `setInterval` at 13 fps with per-step rendering cap out at toy scale (500×500 canvas, ~13 steps/frame) — the contrast confirms rAF + batching is what separates "runs" from "feels fast." — [#! code: Langton's Ant in JavaScript](https://www.hashbangcode.com/article/langtons-ant-javascript)

### Inferences
- **Where time goes, in order:** (1) `putImageData`/rasterization of the viewport (~0 µs dirty-rect steady state → ~2 ms worst case full-frame at 4K/DPR2 — see Key Question 2 numbers); (2) GC pauses from any per-frame allocation (ImageData reuse: allocate once per resize, never per frame); (3) the step loop itself (~14 ns/step). Design consequence: make the step loop allocation-free and reuse one ImageData; rendering is already dirty-rect; only then is the loop CPU-bound.
- **Adaptive steps-per-frame controller:** each rAF, measure `dt = now - lastFrameTime`; if `dt < 12 ms`, steps *= 1.25 (capped by a max, e.g. 250K or until step-cost dominates); if `dt > 17 ms`, steps = max(1, floor(steps * dt/16.7)). Multiply by ant count since cost scales with ants. This self-tunes across hardware without a benchmark mode.
- **Speed slider mapping:** map slider position s ∈ [0, 1] to steps-per-second as `stepsPerSec = round(10^(lerp(0, 6, s)))` (1 → 1M steps/s, log-linear feel), then convert to steps-per-frame by elapsed time, carrying remainders (`acc += stepsPerSec * dt; n = floor(acc); acc -= n`) so slow speeds get exact integer steps. Below ~60 steps/s, honor a real-time cadence (1 step/s literally steps once per second).
- **Turbo mode:** run batches of ~10⁶–10⁷ steps inside a rAF (or `setTimeout(0)`) without touching the canvas, then render one frame every ~50 ms so the UI stays live; keep an absolute yield every ≤ 100 ms to keep input responsive. A synchronous 10⁸-step button is acceptable only with an explicit "may freeze ~2 s" affordance. At ~14 ns/step, 10⁸ steps ≈ 1.4 s of pure compute — actually acceptable as a one-shot "fast-forward N steps" action.
- **Worker + SAB vs main thread:** SAB enables true parallel stepping, but (a) ants are inherently sequential through shared grid state — multi-ant stepping needs chunk-level locking, and with 10⁵ ants the contention would dominate; (b) SAB needs COOP/COEP headers which GitHub Pages cannot serve (it serves static files without custom response headers) — so an SAB build breaks the primary deployment target; (c) postMessage of a transferable `ArrayBuffer` (or `ImageBitmap`, or `OffscreenCanvas`) covers the one real cross-thread need (render in worker). **Recommendation:** single main-thread loop; escalate to a plain Worker + `transferControlToOffscreen()` for render decoupling; skip SAB entirely.

### Gaps
- No fetched source directly profiles "JS Langton's ant: % time in step loop vs render vs GC"; the ordering is inferred from the cited GoL benchmarks and canvas measurements. A 10-minute DevTools performance profile on the prototype will confirm it.
- Exact 2026 status of `document-isolation-policy` (the COOP/COEP replacement that eases SAB deployment) was surfaced but not confirmed as shipped; if it lands on GitHub Pages-hosted origins, revisit the SAB verdict. — [WICG/document-isolation-policy](https://github.com/WICG/document-isolation-policy)

## Key Question 4 — Rule engine design & serialization

### Takeaway
Make the engine **data-driven over a flat transition table**: one `Uint8Array`/`Uint16Array` of size `states × colors`, each entry packing `(writeColor, turn, nextState)`. Presets are then pure data — rule strings like `RL`, `LLRR`, `RRLLLRLLLRRR` (the established multi-color notation) or packed base64 tables for full turmites (Golly's MAP-rule precedent). Ship TypeScript + Vite, not a single file: the engine module must import cleanly into Node for tests, and Vite gives GitHub Pages deployment for free.

### Cited Findings
- The standard multi-color Langton's ant extension (Turk/Propp) is written as a string of turn letters, one per color, cycling colors: e.g. `RLR`, `LLRR`, `LRRRRRLLR`, `RRLLLRLLLRRR` — rule-string-first design is the field's native format. — [Wikipedia: Langton's ant](https://en.wikipedia.org/wiki/Langton%27s_ant)
- Full turmites generalize to three rule matrices indexed [state][color]: a state matrix S (next internal state), a color matrix C (color written), and a turn matrix T (0 = no turn, 1 = right 90°, 2 = 180°, 3 = left 90°) — i.e., any turmite is exactly an `(M×N)` table of `(s', c', t)` triples. — [University of Luxembourg: Turmites report](https://math.uni.lu/eml/assets/reports/2022/turmites.pdf)
- Golly serializes an arbitrary 2-state Moore-neighborhood transition function as a **512-bit table, base64-encoded (86 chars), prefixed `MAP`** — direct precedent for "transition tables as base64 strings are a shareable rule format" and for canonicalizing rules to data. — [Golly Help: QuickLife (MAP rules)](https://golly.sourceforge.io/Help/Algorithms/QuickLife.html)
- A production Langton's Ant toolchain encodes rules as a closed chain of `{on, replace_with, turn}` records and *validates* that the chain is closed (every reachable color has a rule; unreachable states are invalid) — a useful validation rule for a browser editor too. — [nluka/langant-explorer README](https://github.com/nluka/langant-explorer)
- An existing JS CA framework demonstrates the data-driven goal precisely: one engine accepts any rule function ("Game of Life and its variants, elementary automata, Langton's Ant-style turmites, cyclic automata… anything you can express as 'look at a cell and its neighbors, return the next state'"), with turmites as just another rule; presets (`LLRR`, `RRLLLRLLLRRR`, up to four ants) are configuration, not code. — [chirs/cellular_automata README](https://github.com/chirs/cellular_automata)
- Golly plugs in new rules via a `RuleLoader` algorithm that loads rule files at runtime — "rules are data, loaded from strings/files" is the production pattern. — [Golly home page](https://golly.sourceforge.io/)

### Inferences
- **Recommended table layout.** For ants with C colors and no internal state: `turnTable: Uint8Array(C)` with values `L=0, R=1, N=2, U=3` (the step is then: `c = grid[i]; grid[i] = (c+1) % C; dir = (dir + delta[turnTable[c]]) & 3;` — two array reads, one write, no branches). For full turmites with S states: `Uint8Array(S*C)` packing `writeColor` (4 bits) + `turn` (2 bits) into one byte for grid-adjacent work, plus a parallel `Uint8Array(S*C)` for `nextState` — or a single `Uint16Array` packing all three (color 0–15 | turn 0–3 | state 0–15) if S, C ≤ 16. Jumping through a table indexed by `state*C + color` keeps the hot path allocation-free and branch-free.
- **Rule-string grammar (three tiers):**
  1. *Ant string* `^[LRNU]+$` → N colors, no internal state (covers every Turk/Propp rule incl. `RL` = classic Langton).
  2. *Turmite tuple string* for M×N rules: comma-separated triples `turn/write/state` per (state,color) cell — human-editable in a UI grid.
  3. *Base64 table* for arbitrary tables, mirroring Golly's `MAP` scheme (pack nibbles → base64) — used for shareable URLs and import/export.
- **Presets as data:** ship a `presets.ts` exporting `{ name, ruleString, antSeeds, colors, description }[]`; adding a preset requires zero engine changes. Known-good seeds from the literature: `RL` (highway ~11,000 steps), `RLR` (chaotic, highway unknown — a nice "mystery" preset), `LLRR` (symmetric), `LRRRRRLLR` (fills square), `LLRRRLRLRLLR` (convoluted highway), `RRLLLRLLLRRR` (filled triangle after ~15,900 steps). — [Wikipedia: Langton's ant](https://en.wikipedia.org/wiki/Langton%27s_ant), [chirs/cellular_automata](https://github.com/chirs/cellular_automata)
- **Single file vs TS + Vite:** a no-build vanilla setup demonstrably works (chirs/cellular_automata serves a static `www/` dir with zero dependencies and tests with Node's built-in runner in CI). But for a portfolio piece TypeScript + Vite wins: typed engine module importable by both Vitest (Node, no DOM) and the browser app; `vite build` produces exactly the static `dist/` that GitHub Pages wants; workers and minification configured by default. Runner-up: no-build vanilla if you want "view source" purity. — [chirs/cellular_automata](https://github.com/chirs/cellular_automata), [Vite: Building for Production](https://vite.dev/guide/build)
- **Architecture shape:** strict layering so the engine never touches the DOM: `engine/` (grid, rule, stepper — pure, integer-only, no allocations in `step`), `render/` (world texture + viewport compositor), `app/` (rAF loop, UI, URL encoding). This is also what makes headless unit tests (Key Question 6) possible.

### Gaps
- No canonical Golly-compatible file format exists for turmites with internal state (Golly supports generative rule tables but not ants natively); the base64-table scheme proposed here is modeled on Golly's `MAP` format but is custom — document it in the repo README and provide an importer for plain ant strings (`RL…`) so the format isn't load-bearing.
- The exact provenance/attribution of the letter-string notation (Turk's writeup) was cited via Wikipedia; the original Turk paper URL was not fetched.

## Key Question 5 — Persistence & determinism

### Takeaway
Three persistence tiers: **URL hash** for shareable small runs (`#rule=RL&…` + RLE/base64 grid, the pattern proven by chirs/cellular_automata's Share button), **download/upload file** (RLE or packed-base64 JSON) for full state, and **localStorage** for UI prefs. Determinism comes free from pure integer math plus an app-seeded PRNG (never `Math.random`) — replay a run by re-stepping from the seed, and verify with a cross-engine golden-hash test.

### Cited Findings
- chirs/cellular_automata ships exactly the URL-state pattern: "Shareable URLs — `#cyclic` links to a rule; the Share button encodes the entire grid state in the URL (run-length encoded), so a drawing can be sent as a link," plus standard RLE import/export ("paste a pattern from LifeWiki or Golly… or drop a .rle file"). — [chirs/cellular_automata README](https://github.com/chirs/cellular_automata)
- RLE is the interoperability standard: Golly "reads RLE, macrocell, Life 1.05/1.06, dblife, and MCell files" — a bare-bones RLE encoder/decoder (`3b2o$...!` syntax) is both a portfolio credibility signal and free interop with the LifeWiki/Golly ecosystem. — [Golly home page](https://golly.sourceforge.io/)
- Production state format precedent (nluka/langant-explorer): JSON with `generation`, grid dimensions, grid state, ant orientation/position, and the rule table; plus PGM image exports of the grid — i.e., **step count + rule + ant pose + grid** is the complete, sufficient state vector for an ant sim. — [nluka/langant-explorer README](https://github.com/nluka/langant-explorer)
- The ant's entire world state is tiny in another sense: grid state + ant position + direction + rule is all there is — "The ant carries almost no memory: only its position on the grid and the direction it currently faces" — which makes URL-hash sharing of *rule + ant seed + step count* sufficient for deterministic replay of the classic rules (no grid needed) as long as ant starts are data. — [Langton's Ant field notebook](https://langton-ant-tau.vercel.app/)
- Behavior benchmarks for replay validation exist in the literature: the classic `RL` ant settles onto its highway after about 10,000–11,000 steps, and the `RRLLLRLLLRRR` triangle emerges after ~15,900 iterations — deterministic golden tests can assert "highway detected by step N." — [Wikipedia: Langton's ant](https://en.wikipedia.org/wiki/Langton%27s_ant), [University of Luxembourg: Langton's Ant report](https://math.uni.lu/eml/assets/reports/langton.pdf)

### Inferences
- **URL-hash scheme (recommended):** `#r=<ruleString>&a=<packedAnts>&s=<steps>&g=<rleBase64url>` — rule string (plain text), ants as base64-packed (x:i16, y:i16, dir:2bits) records, step count as base36, grid only when small (<~4 KB encoded, since RLE of a mostly-zero world is tiny for early states). For long runs, encode only the *visited bounding box* (chunks touched), not the infinite plane — the rest is color 0 by definition. Keep total under ~8 KB (browser-dependent URL limits; ~2048 chars is the only universally safe guarantee for maximal compatibility, so treat hash-encoding of large grids as best-effort with a "state too large for URL — copy to file instead" fallback).
- **Determinism recipe:** (1) all grid/step math in integers (coords are `Int32Array`/i32; no floats in the step path); (2) seeded PRNG (e.g., mulberry32/xoshiro128**) for any "random scatter N ants" preset, with the seed stored in the URL/save; `Math.random()` is spec'd to be non-seedable, so it must never feed the simulation; (3) iteration order is irrelevant for ants (they're not synchronous-update cellular automata — each step touches one cell), which removes a whole class of cross-engine divergence that plagues Life replayers. JS integer semantics are fixed by spec (Number ops on ints up to 2⁵³, `| 0`/`>>> 0` for 32-bit), so pure-integer JS step code replays identically in every browser.
- **State vector (full save):** `{ version, rule, colors, rngSeed, stepCount, ants: [{x, y, dir, state}], grid: { bbox, chunkRLE | base64 } }` — exactly the fields nluka's JSON format uses (generation/grid/ant/rules) plus a version tag for forward compatibility.
- **Replay-as-save:** for classic rules, saving just `rule + seed + ant poses + step` (few dozen bytes) replays any run at up to ~10⁸ steps/s — implement "scrub through a run" as re-simulation with checkpoints every 10⁶ steps (store snapshots) if scrubbing feels sluggish.

### Gaps
- No fetched source documents current browser URL-length limits for `location.hash` specifically (the fragment is never sent to the server, but navigation limits differ); the ~2048-char safe figure is the old standard — verify against target browsers or just cap encodes at ~1 KB.
- `performance.now()` determinism is irrelevant to the sim but note: no source was fetched confirming integer-only JS is *formally* specified deterministic; this is universal engine behavior (IEEE 754 + spec'd operators), treat as safe by construction, and pin it with a cross-browser golden-hash CI test (Key Question 6).

## Key Question 6 — Testing, CI & deployment

### Takeaway
Layer the tests where each is cheap: **headless Vitest unit tests** of the pure engine (rule tables, stepping, RLE codec), **property tests** of invariants (exactly one cell flips per single-ant step; ant moves exactly one cell; direction stays in 0–3), a **golden-hash determinism test** across Node versions, and a **Playwright smoke test** that loads the page, steps N times, and asserts via screenshot diff (`toHaveScreenshot` with `maxDiffPixels`) plus DOM-read assertions. Deploy the Vite build to GitHub Pages via the official Actions workflow (Source: GitHub Actions), with `base: '/<REPO>/'`.

### Cited Findings
- Engine tests don't need a browser: chirs/cellular_automata runs `npm test` with **Node's built-in test runner, in CI on push**, against the same engine code the browser uses — the vanilla-JS CA framework precedent for headless engine testing. — [chirs/cellular_automata README](https://github.com/chirs/cellular_automata)
- The wasm-bindgen tutorial tests its Rust universe headlessly (`wasm-pack test --chrome --headless` / `--firefox`) by stepping a known pattern and asserting the exact resulting cell array — the same "known input → known output" golden pattern works for a TS engine in Vitest. — [Rust and WebAssembly book: Game of Life testing chapter](https://github.com/rustwasm/book/blob/master/src/game-of-life/testing.md)
- Playwright Test has first-class visual regression: `await expect(page.locator('canvas#app')).toHaveScreenshot()` with `maxDiffPixels`/`maxDiffPixelRatio`/`threshold` options (uses pixelmatch), auto-generates baselines on first run, and supports `.png`/`.webp`; canvas interaction via `locator.click({ position: { x, y } })` and drag via `mouse.down/move/up`. — [Playwright docs: Visual comparisons](https://playwright.dev/docs/test-snapshots), [Playwright PageAssertions API](https://playwright.dev/docs/api/class-pageassertions), [community canvas-testing guide](https://github.com/testdino-hq/playwright-skill/blob/main/core/canvas-and-webgl.md)
- Playwright explicitly warns screenshots "can vary based on the host OS, version, settings, hardware, power source, headless mode" — so baselines must be generated/updated per CI environment (`--update-snapshots`) and pixel assertions need tolerance. — [Playwright docs: Visual comparisons](https://playwright.dev/docs/test-snapshots)
- GitHub Pages deployment for Vite is officially documented: set `base: '/<REPO>/'` in `vite.config` (or `'/'` for user/organization pages and custom domains), switch repo Settings → Pages → Source: **GitHub Actions**, and add a `deploy.yml` using `actions/upload-pages-artifact@v5` on `./dist` + `actions/deploy-pages@v5`; Vite supports "relative base" (`base: './'`) if you don't know the final path. — [Vite: Deploying a Static Site](https://vite.dev/guide/static-deploy), [Vite: Building for Production](https://vite.dev/guide/build)
- Invariant source for property tests: the ant rule defines the exact per-step side effects — "At a white square, turn 90° clockwise, flip the color of the square, move forward one unit" (one cell flips, one cell of movement) — so `changedCells == 1` and `|Δx|+|Δy| == 1` per step are provable invariants for single-ant rules, and per-ant for multi-ant. — [Wikipedia: Langton's ant](https://en.wikipedia.org/wiki/Langton%27s_ant)

### Inferences
- **Recommended test matrix:**
  1. *Unit (Vitest, Node):* rule-string parser (accepts `RL`, rejects `XYZ` when C=2), table construction, `step()` on a 3×3 world with hand-computed outcomes, RLE/base64 round-trips, save/load round-trip, chunk boundary crossing (ant stepping across a 64×64 chunk edge), eviction/refcount logic.
  2. *Property (fast-check under Vitest):* for random rules and random starting cells — exactly one cell changes per step; ant always moves to an adjacent cell; `dir` always in `[0,3]` without `%` drift; after K steps, cells touched ⊆ K-neighborhood; serialize→deserialize→step ≡ step (state round-trip identity).
  3. *Golden determinism:* run `RL` 11,000 steps → hash the grid (`FNV-1a` over the visited bbox) and compare against a committed constant; reruns in CI (any Node version, any OS) must match — this is the cross-browser determinism proof, extended by a Playwright run that reads the same hash out of the page via `page.evaluate(() => window.__sim.hash())` and compares to the same constant. Highway-formation assertions (e.g., "by step 11,000 the highway's periodic window is intact") are possible but fiddly; the hash is the robust version. — thresholds grounded in [Luxembourg report: highway ~11,000 steps](https://math.uni.lu/eml/assets/reports/langton.pdf)
  4. *Playwright smoke:* load `dist/` via `vite preview`, assert canvas visible, dispatch `page.evaluate` to run 200 fixed steps, then `toHaveScreenshot` (Chromium-only project in CI to avoid multi-browser baseline churn) with `maxDiffPixelRatio` ~0.01, plus click-on-canvas → state changed. Keep screenshots deterministic by disabling CSS animations (built-in `animations: 'disabled'` option). — [Playwright docs](https://playwright.dev/docs/test-snapshots)
- **CI pipeline (GitHub Actions, one workflow file for tests + one for deploy):** `npm ci` → `vitest run` → `tsc --noEmit` → `npx playwright install --with-deps chromium` → `playwright test` (against `vite preview`) → on push to `main`: the official Pages deploy job (actions/configure-pages + upload-pages-artifact@v5 + deploy-pages@v5). Vite's docs ship the exact deploy.yml to copy. — [Vite: Deploying a Static Site](https://vite.dev/guide/static-deploy)
- **Deployment caveats:** project pages live under `/langtons-ant/` → set `base: '/langtons-ant/'` (or `base: './'`); if any future feature needs SAB/threads, GitHub Pages' lack of custom response headers blocks it (see Key Question 3) — design around postMessage instead.
- **Single deploy job, no gh-pages branch:** the Actions-artifact flow replaces the old `gh-pages` push pattern and keeps history clean.

### Gaps
- No fetched benchmark compares Vitest vs Node test runner startup on CI; either is defensible — Vitest chosen for property-testing library compatibility (fast-check) and watch mode; note as a free choice, not a measured one.
- Exact Playwright canvas behavior in headless Firefox with hidden canvases had a 2021 bug report (screenshots not captured when canvas is hidden); latest status unconfirmed — keep the smoke test's canvas visible and Chromium-only to sidestep it. — [Playwright issue #8000](https://github.com/microsoft/playwright/issues/8000)

## Cross-cutting recommendation summary (for the report writer)

| Decision | Recommended | Runner-up | Deciding numbers |
|---|---|---|---|
| Grid storage | Chunked grid: `Map<packedKey, Uint8Array(64×64)>`, lazy create, 1 B/cell | Sparse `Map<packedXY,color>` for ≤10⁷ live cells only | ≤100–200 MB after 10⁸ ant steps vs ~4–8 GB for sparse Map; Golly (production) uses tiles + 256 states — [Golly](https://golly.sourceforge.io/), [langant-explorer](https://github.com/nluka/langant-explorer) |
| Rendering | Offscreen world texture (1px/cell) + dirty-rect `putImageData` + single scaled `drawImage`, smoothing off | WebGL2 texture + palette shader (only if >4K @ DPR2 or heavy overlays) | full-frame putImageData ≈ 50 µs @ 320×180 (~1.8 ms @ 4K) vs dirty-rect ≈ 0 in steady state; drawImage blit ≈ 1.15M ops/s vs putImageData 16K ops/s; per-pixel fillRect 30–100× slower — [MeasureThat ×3](https://www.measurethat.net/Benchmarks/Show/33628/1/clearing-canvas-v2) |
| Threading | Main thread rAF loop; optional OffscreenCanvas-in-Worker | Worker + SharedArrayBuffer | SAB needs COOP+COEP headers — not servable on GitHub Pages; ants are sequential through shared state — [web.dev](https://web.dev/articles/coop-coep) |
| Scheduling | Adaptive steps-per-frame vs ~10 ms budget; log slider 1 → 1M steps/s; turbo = render-skipping batches with ≤100 ms yields | Fixed user-chosen steps-per-refresh (langtonant.com style) | Step cost ≈ 14 ns (73M cell-updates/s measured); a frame budget of 10 ms ≈ 700K steps of headroom before render matters — [chirs/cellular_automata](https://github.com/chirs/cellular_automata), [langtonant.com](http://www.langtonant.com/) |

| Persistence | URL hash (rule + ants + step, RLE/base64url grid when small) + JSON save file + RLE import/export | Full-grid-in-URL always | chirs/cellular_automata ships URL-RLE sharing and RLE import/export today — [chirs/cellular_automata](https://github.com/chirs/cellular_automata); nluka JSON state precedent — [langant-explorer](https://github.com/nluka/langant-explorer) |

| Testing | Vitest unit + property (fast-check) + golden hash; Playwright Chromium smoke w/ `toHaveScreenshot` | Screenshot tests across all 3 engines in CI (baseline churn) | Playwright `toHaveScreenshot` with `maxDiffPixels`, env-dependent rendering warning — [Playwright docs](https://playwright.dev/docs/test-snapshots) |
