# Presenting an Interactive Langton's Ant / Turmite Simulator as a Standout Portfolio Artifact

Research date: October 2026. Scope: presentation formats, reviewer signals, shareability mechanics, experience differentiation, interview talking points, and viral precedents for a browser-based turmite simulator built as a personal-portfolio project (GitHub: Exios66). Reference sites to exceed: https://langtonant.com/ and https://evolvecode.io/turmites/index.html (both directly fetched and benchmarked below).

## How do strong engineering portfolios present interactive/simulation projects?

### Takeaway
Top portfolios run a two-layer system: the **repo carries credibility** (GIF demo, badges, architecture diagram, quickstart, tests, perf numbers) and the **portfolio/demo page carries narrative** (a Ciechanowski-style case study that opens with a live, touchable model). Reviewers spend under 90 seconds per profile and ~60 seconds per project, so the live demo must work on first click and the README must communicate value in the first screen.

### Cited Findings

**The reviewer's actual scan pattern (timed):**
- Hiring managers follow a ~60-second funnel: skim homepage (10s) → click one featured project (20s) → scan code (20s) → check GitHub profile (10s). The featured project must have a working live demo and a real README. — [DevPlaybook, "Developer Portfolio Checklist: 20 Things Hiring Managers Look For" (2026)](https://devplaybook.cc/blog/developer-portfolio-checklist-20-things-hiring-managers/)
- Recruiters spend under 90 seconds on a GitHub profile before deciding whether to dig deeper; what matters is 2–4 pinned repos with clear READMEs and real functionality, not repo count. — [Scalyz, "The Importance of Portfolios and GitHub Profiles"](https://blog.scalyz.com/en/portfolios-github-profiles-hiring)
- Per a Stack Overflow survey cited by Scalyz, roughly 71% of hiring managers consider a candidate's GitHub activity for technical roles. — [Scalyz](https://blog.scalyz.com/en/portfolios-github-profiles-hiring)

**Case-study structure and where the story lives:**
- Each project's description should "outline their thought process from the initial stages through to completion," including key decisions and obstacles overcome — i.e., an explicit problem → approach → decisions → outcomes arc. — [Techtrust, "How to Evaluate Key Projects in Developer Portfolios"](https://www.techtrust.com/post/key-projects-in-developer-portfolios-for-hiring)
- A hiring manager's own template for project presentation: tech stack + methodologies, then bulleted impact/outcome statements that are quantifiable, plus a live link; add write-ups covering "what you've learned, what challenged you, what you're proud of, what you'd do better." — [Alishah Novin, "FAQs for a Software Engineering Hiring Manager"](https://blog.alishahnovin.com/2022/07/faqs-of-software-engineering-hiring.html)
- The four questions a project must answer fluently to be interview-ready: What problem does this solve and for whom? What was the hardest technical decision? What would you do differently if you rebuilt it today? What broke and how did you fix it? — [LastRound AI, "Side Projects vs GPA for Tech Jobs" (2026)](https://lastroundai.com/blog/side-projects-vs-gpa)
- Evidence of iteration is a hiring signal in itself: a 200-commit git history "tells a story"; 3 commits reads as one-sitting tutorial work. A deployed URL that works *right now* beats screenshots; a broken demo "tells me something about how you treat production code." — [Solid Web, "How to Get Your First Developer Job in 2026 (From Someone Who Hires)" (2026)](https://solid-web.com/first-developer-job/)

**README design (what the best repos actually do):**
- Canonical README hierarchy: logo/banner → one-sentence description → tidy badge row → **animated demo GIF immediately after the fold** → copy-paste quickstart → Mermaid architecture diagram (renders natively in GitHub Markdown, diffs cleanly in PRs) → TOC → features → docs links. Priority order for what moves stars: (1) animated demo, (2) README hero + quickstart, (3) launch thread, (4) architecture diagram, (5) OG social card. — [glamworks/glamfire research doc on multimedia assets](https://github.com/glamworks/glamfire/blob/main/research/17-multimedia-assets.md)
- An audit of the most successful open-source READMEs found demo GIFs are "the single biggest missed opportunity" — only a minority of even excellent repos use animated demos, which makes it a cheap differentiator. Exemplars: Meilisearch (animated demo GIF with light/dark variants, 7 live demo apps linked from README, benchmark charts at top), Dioxus (every feature section has its own visual), Terminal.Gui (hero animation + demo GIF + runnable quickstart). — [kerryhatcher/banger-readme exemplary-READMEs audit](https://github.com/kerryhatcher/banger-readme/blob/main/docs/exemplary-readmes.md) and [examples-audit.md](https://github.com/kerryhatcher/banger-readme/blob/main/docs/examples-audit.md)
- Elements of beautiful READMEs per the awesome-readme canon: GIF demo, TOC, badges, logo; for architecture, dedicated ARCHITECTURE.md files with diagrams and invariants (esbuild, VS Code, Tauri, Flutter Engine cited as exemplars). GIF tools: Gifski (free, high quality), ScreenToGif (free), Gifox; GitHub's 10MB embed limit — drag-and-drop upload onto a GitHub CDN URL avoids bloating the repo. Encoding a GIF with a `.png` extension forces autoplay in some README contexts. — [matiassingers/awesome-readme](https://github.com/matiassingers/awesome-readme) and [jacobmarks/ultimate-project-readme](https://github.com/jacobmarks/ultimate-project-readme)
- Scripted, CI-regenerable demos: VHS (Charmbracelet) `.tape` files render to GIF/MP4/WebM and can be re-rendered in CI on release so the demo never drifts from reality. For a canvas app this maps to a Playwright/puppeteer-driven capture script committed to the repo. — [glamfire research doc](https://github.com/glamworks/glamfire/blob/main/research/17-multimedia-assets.md)

**The gold standard for presentation — Bartosz Ciechanowski (ciechanow.ski):**
- Every figure is a hand-coded live simulation running in the reader's browser; no stock illustrations, no frameworks — bare WebGL ("just bare webGL... it gives me complete control"), 3D models in Shapr3D/Blender, animations done by hand; interactive frame rates with complex physics. — [HN thread on Cameras and Lenses](https://news.ycombinator.com/item?id=27000223), [mangodeveloper teardown of "Sound"](https://mangodeveloper.com/articles/bartosz-ciechanowskis-interactive-sound-article-is-the-best-physics-explainer-youll-play-with-all)
- Structural pattern every article follows: (1) open with a working model plus an explicit instruction to touch it ("You can drag the device around…"); (2) ramp from simple toy to real system ("step-by-step improve upon it," "build a camera from first principles"); (3) narrate what to notice ("Notice that as soon as you let go…"); (4) openly admit where the model lies/simplifies; (5) respect the reader's machine (global animation pause to save power, imperial/metric toggle, click/tap swap). — [learn-ui.com, "Explorable explanations"](https://learn-ui.com/chapters/explaining/explorable-explanations)
- His 'Sound' article scored 237 points on Hacker News; the archive is only ~20 articles in a decade because each takes months — rarity itself is part of the prestige. — [mangodeveloper](https://mangodeveloper.com/articles/bartosz-ciechanowskis-interactive-sound-article-is-the-best-physics-explainer-youll-play-with-all), [Ryan Orban's notes](https://ryanorban.com/notes/bartosz-ciechanowski-blog/)
- Relevance to a portfolio: Ciechanowski is cited as the exemplar of "explorable explanations" and of blending design and engineering for educational content; the genre is defined as "the reader operates the subject instead of reading about it." — [learn-ui.com](https://learn-ui.com/chapters/explaining/explorable-explanations), [Cool People Stories profile](https://www.coolpeoplestories.com/bartosz-ciechanowski-interactive)

**Benchmark: the two sites to exceed (fetched directly):**
- **langtonant.com** is a bare simulator: starting-orientation buttons, a "Custom Behavior" text field, grid-size select (50×50 up to 5000×5000), steps-per-refresh (1 to 500,000), delay-per-refresh, a live step count, and links to source/Wikipedia. No narration, no gallery, no stats beyond step count, no sharing/permalinks, no theming, no export, no explanation of why the ant matters. Its strength is raw grid scale and simplicity. — [langtonant.com](https://langtonant.com/) (source: [coder369/langtons-ant](https://github.com/coder369/langtons-ant))
- **evolvecode.io/turmites ("Langton's Ant Colony")** is stronger: multiple simultaneous ants, per-ant rule editing with presets, start position/direction controls, a randomize panel (max states, max colors, relative/absolute/random movements), steps/sec readout, pause/reset/fullscreen. Still no narrated gallery, no milestone detection, no permalinks/sharing, no stat overlays beyond steps/sec, no export. — [evolvecode.io/turmites/index.html](https://evolvecode.io/turmites/index.html)
- Third competitive datum: **cenonym/trmt** (terminal turmite, Rust, 85 stars, created June 2025) — demo GIF at top of README, up to 256 simultaneous heads, full Unicode/color support, randomized rule generator with "roughly 10^15 possible rules," and deterministic seed-based simulation for reproducible patterns. Seeds-for-reproducibility is a feature the web competitor already ships. — [cenonym/trmt](https://github.com/cenonym/trmt)

### Inferences
- The winning split of story: **repo = proof** (README with GIF, Mermaid architecture diagram, tests, benchmark table, quickstart that runs the sim in one command or opens the live URL); **portfolio page = narrative** (case study: why the ant is scientifically interesting → design decisions → architecture → measured outcomes → live embed); **demo page = the wow surface** (instant first paint, one ant already running so the first frame moves).
- Adopt the Ciechanowski arc at portfolio scale: open the project page with a running ant and the line "click to disturb it," then ramp: the two-state rule → why ~10k steps of chaos → the highway → generalized turmite rule tables → the universality result. Each section anchored by a live control, not a screenshot.
- Since langtonant.com and evolvecode.io are both control-panels-without-narrative, the cheapest differentiator is **story + shareability**, not more simulation options: a narrated gallery, permalinks, and stat overlays directly exploit their gaps.

### Gaps
- No quantitative 2025–2026 data on what fraction of reviewers actually click live-demo links (sources are qualitative hiring-manager testimony).
- The evolvecode.io page is JS-heavy; some features (e.g., hidden share buttons) may exist but were not visible in the fetched DOM. Noted as a caveat.

## What signals do hiring managers/reviewers actually value in a side project like this — and how to surface each?

### Takeaway
Reviewers reward **shipped-and-live, readable, quantified, and validated**. Every signal you want credit for must be made explicit in under 10 seconds of looking: a working URL, a README with an architecture diagram and tests, bullets with before→after numbers, and a form of external validation (users, stars, a post that got traction). Position the project as *engineering excellence on a tiny canvas*, and give it at least one truthful superlative.

### Cited Findings
- **Live and working beats polished and broken**: "A broken or unavailable demo is worse than no demo"; use free hosting (Vercel/Netlify/GitHub Pages) and re-check demo links before applying. — [DevPlaybook](https://devplaybook.cc/blog/developer-portfolio-checklist-20-things-hiring-managers/)
- **The 30-second code test**: pick any file — can a senior engineer understand it in 30 seconds? Dense, cryptic code signals how you'd code on the job. — [DevPlaybook](https://devplaybook.cc/blog/developer-portfolio-checklist-20-things-hiring-managers/)
- **Tests**: zero tests on every project "signals that you don't test in your normal workflow"; even basic unit tests on core logic (for this project: rule stepping, state transitions, URL serialization round-trips) count. — [DevPlaybook](https://devplaybook.cc/blog/developer-portfolio-checklist-20-things-hiring-managers/)
- **Commits**: "fix", "wip" commit messages undercut you; messages like "Add rate limiting to auth endpoint to prevent brute force" communicate engineering judgment. Hiring managers do browse commit history. — [DevPlaybook](https://devplaybook.cc/blog/developer-portfolio-checklist-20-things-hiring-managers/)
- **README contents expected**: one-paragraph description of what it does, run-locally commands, architecture overview or key technical decisions ("optional, but impressive"), screenshots/GIFs of the app in action. — [DevPlaybook](https://devplaybook.cc/blog/developer-portfolio-checklist-20-things-hiring-managers/)
- **Validation is what makes a side project land on a resume**: numbers of users/visitors/stars, competition wins, press/publicity links. Give each project 1–3 bullets, each with description + a form of validation; links rarely get clicked, but if clicked they must wow (README doing the showcasing). — [CodePath, "How to Have Side Projects That Stand Out and Why" (2024)](https://www.codepath.org/news/how-to-have-side-projects-that-stand-out-and-why/)
- **Superlatives**: describe any side project truthfully in at least one "best" — biggest, most downloaded, fastest, most praised — and lead with the aspect that shows you "in the most outrageously positive light" (technical complexity, scale, results, relevance). — [Microsoft Learn / MSDN "Upstart" column](https://learn.microsoft.com/en-us/archive/msdn-magazine/2017/january/upstart-you-re-hired-11-things-to-consider-with-side-projects)
- **List placement nuance** (conflicting advice, reported as such): the MSDN column argues side projects belong under Work Experience (claiming a Projects section "discounts its value by 75 percent"); CodePath explicitly recommends a Projects section and says avoid Work Experience unless paid. — [Microsoft Learn](https://learn.microsoft.com/en-us/archive/msdn-magazine/2017/january/upstart-you-re-hired-11-things-to-consider-with-side-projects); contradicted by [CodePath](https://www.codepath.org/news/how-to-have-side-projects-that-stand-out-and-why/)
- **Quantified bullet formula** (for résumé and case study alike): action verb + what you did + how + measurable outcome, ideally with baseline → after, e.g., "Reduced p95 latency from 1.5s → 350ms (77%)". Front-load the outcome; "significantly improved performance" reads as filler. — [techinterview.org, "Quantifying Impact on Engineering Resumes" (2026)](https://www.techinterview.org/post/3233474604/quantifying-impact-engineering-resume/), [thita.ai quantification guide (2026)](https://thita.ai/blog/resume/how-to-quantify-impact-on-your-resume-as-a-developer)
- **Side-project-specific metrics that count even with no users**: scale and scope numbers are acceptable ("3 releases/week", approximations fine); the measurable-result pattern is the point, not the size. — [dev.to, "How to Quantify Resume Bullet Points" (2026)](https://dev.to/prat_naik/how-to-quantify-resume-bullet-points-with-50-real-examples-38ma), [WriteCV, 50 quantified examples (2026)](https://writecv.ai/blog/how-to-quantify-resume-bullets)
- **Weak signals to not over-invest in**: the green contribution graph "predicts almost nothing"; star count is "often unrelated to quality." Substance = pinned repos, READMEs, one or two tested and documented projects. — [Scalyz](https://blog.scalyz.com/en/portfolios-github-profiles-hiring)
- **Range matters**: an ideal portfolio shows one UI-heavy project, one algorithmic/data-heavy project (CS fundamentals), one with infrastructure considerations. A turmite simulator is the archetypal "algorithmic/CS fundamentals" entry — lean into the algorithms/performance angle rather than dressing it up as a CRUD app. — [DevPlaybook](https://devplaybook.cc/blog/developer-portfolio-checklist-20-things-hiring-managers/)
- **Production thinking as differentiator**: candidates who can narrate a tradeoff ("I chose X because I expected Y") outperform perfect codebases with no reasoning; interviewers remember "having an opinion about what you built." — [LastRound AI](https://lastroundai.com/blog/side-projects-vs-gpa), [Solid Web](https://solid-web.com/first-developer-job/)

### Inferences
- Mapping each signal to an explicit surface for this project: **architecture clarity** → Mermaid diagram in README + an ARCHITECTURE.md section naming the engine/render/interaction layers; **performance engineering** → a benchmark table (steps/sec at grid sizes, vs. langtonant.com's batched-refresh approach) with the method stated; **tests** → badge + one-line "core engine covered by N unit tests including property tests of rule tables"; **UX polish** → the GIF itself; **shipped** → "Try it live" link as the first line of both README and resume bullet.
- The sim's honest superlatives to pick from (fill in measured values): "renders N million steps/min in-browser, zero dependencies"; "runs a 2,500×2,500 grid at 60fps"; "every run permalinkable"; "rule space of ~10^15 exploreable configs" (the last is trmt's claim for a similar generator — [cenonym/trmt](https://github.com/cenonym/trmt)).

### Gaps
- None of the sources quantify how much README visuals convert reviewer attention into interviews; all evidence is practitioner judgment.

## Shareability & embedding best practices (GitHub Pages, iframes, OG cards, permalinks, exports)

### Takeaway
Every shared link is free advertising: set OG/Twitter meta on the demo page, upload a 1280×640 repo social preview, put OG images behind absolute HTTPS URLs, and validate with the Facebook/LinkedIn debuggers (platforms cache aggressively). Make every run permalinkable by serializing full sim state into the URL, and ship one-click PNG/GIF/WebM export so others advertise the project for you.

### Cited Findings
- **Repo social preview**: Settings → Social preview → upload; PNG/JPG/GIF under 1MB, at least 640×320 (1280×640 recommended); transparent PNG is beneficial because many platforms have dark mode. This controls the unfurl whenever the bare repo URL is shared. — [GitHub Docs, "Customizing your repository's social media preview"](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/customizing-your-repositorys-social-media-preview)
- GitHub now auto-generates Open Graph card images for repos, issues, PRs, and commits (served from `https://opengraph.githubassets.com/1/<owner>/<repo>`), but a custom upload overrides the default for the repository card. — [GitHub Blog, "A framework for building Open Graph images" (2021)](https://github.blog/open-source/git/framework-building-open-graph-images/), [yashsingh.us guide](https://www.yashsingh.us/blog/post/open-graph-image-github-repo)
- **Demo-page meta tags**: the five that matter are `og:title`, `og:description`, `og:image`, `og:url`, `og:type`, plus `twitter:card="summary_large_image"` (big hero image; X falls back to OG tags when twitter:* are absent). `og:image` must be an absolute HTTPS URL — relative paths silently break every validator. Recommend 1200×630 with content centered because platforms crop edges. — [DrinkBird, "Open Graph and Twitter cards"](https://blog.drinkbird.com/courses/jekyll-engineering-blog-github-pages/04-production-polish/02-open-graph-and-social-previews/), [OG Fixer, "GitHub Pages Open Graph Tags"](https://ogfixer.com/blog/github-pages-open-graph-tags)
- **Validation and cache-busting**: use Facebook Sharing Debugger (shows parsed tags, forces re-scrape) and LinkedIn Post Inspector; every platform caches scrapes for hours to days — LinkedIn reportedly caches link previews for 7 days; adding `?v=2` to a changed link sometimes forces X to re-fetch. Mastodon and Slack read OG directly, so a passing Facebook debugger usually predicts correct rendering there. — [DrinkBird](https://blog.drinkbird.com/courses/jekyll-engineering-blog-github-pages/04-production-polish/02-open-graph-and-social-previews/), [Stack Overflow, "Customize preview image for github pages"](https://stackoverflow.com/questions/62743304/customize-preview-image-for-github-pages)
- **GitHub Pages specifics**: fully static hosting is ideal for crawlers (pre-built HTML, no JS execution) — but that also means OG tags must be baked into each HTML file manually (or via a static-site generator include), since there's no server-side logic. With a custom domain, canonicalize `url:` and keep absolute OG URLs on the custom domain. — [OG Fixer](https://ogfixer.com/blog/github-pages-open-graph-tags)
- **Automated OG generation** if the demo grows pages: `@vercel/og` + satori (HTML/JSX → PNG), or a GitHub Action that generates per-page OG images in CI; GitHub's own OG service is a Node app piping template HTML through Puppeteer screenshots — the same technique works to generate a *simulation-screenshot* OG card showing an actual ant run. — [glamfire research doc](https://github.com/glamworks/glamfire/blob/main/research/17-multimedia-assets.md), [GitHub Blog](https://github.blog/open-source/git/framework-building-open-graph-images/)
- **Prior art for "state-as-link" sharing** in adjacent tools: turingmachinesimulator.com saves machines as links ("Machine saved as link"); turingsim.com offers "Save, load and share your machines"; cenonym/trmt offers deterministic seed-based reproducible runs. The pattern is established and users of these tools expect it. — [turingmachinesimulator.com](https://turingmachinesimulator.com/), [turingsim.com](https://turingsim.com/), [cenonym/trmt](https://github.com/cenonym/trmt)
- **Export formats by channel**: GIF for README (GitHub embed limit 10MB; compress with ffmpeg/XConvert), MP4/WebM for X/LinkedIn/short-form which prefer real video over GIF. — [glamfire research doc](https://github.com/glamworks/glamfire/blob/main/research/17-multimedia-assets.md), [jacobmarks/ultimate-project-readme](https://github.com/jacobmarks/ultimate-project-readme)

### Inferences
- **Permalink design** (inference; no dedicated source found — noted as a gap): serialize the complete run definition — rule table, grid size, ant position/direction, seed, step count, theme — into the URL (hash or query params, updated via `history.replaceState` throttled to ~1/sec). Hash-based state (`#rule=RL&steps=10000`) needs no server config on GitHub Pages and keeps the OG card URL stable. Every gallery exhibit then has a "copy link" button, and reviewers can share an exact mid-highway moment. The `og:url` stays canonical (no per-state OG images on static hosting).
- **Iframe embed** for the portfolio case study: host the sim on GitHub Pages, embed with a fixed aspect-ratio `<iframe>` + `loading="lazy"` + a poster/first-frame image so the case-study page stays fast (DevPlaybook flags <2s load as a reviewer requirement). A "fullscreen" escape link inside the iframe covers small viewports.
- **One-click export** (inference): PNG snapshot is trivial from canvas (`toDataURL`); WebM/GIF via `MediaRecorder` on `canvas.captureStream()` or a headless-capture script committed to the repo; a preset "clip the highway forming" export (steps N→N+k) turns every user into a distributor.
- Social-card image for the repo should be a *screenshot of a real run* (highway visible), not a logo — it demonstrates the product in the unfurl, mirroring how Meilisearch's README demo GIF "shows real value, not just a terminal recording." — [banger-readme audit](https://github.com/kerryhatcher/banger-readme/blob/main/docs/examples-audit.md)

### Gaps
- No authoritative source found specifically covering URL-state serialization conventions for canvas sims (hash vs. query param trade-offs, size limits) — the design above is inferred from adjacent evidence (saved-machine links, seed reproducibility).
- Current (2026) OG image size guidance is consolidated at 1200×630 for pages and 1280×640 for GitHub repo previews; X's Card Validator moved behind login — its behavior was verified only via secondary sources.

## Which experience features create "wow" for a turmite simulator specifically?

### Takeaway
The two sites to beat are control panels; the winning moves are **narrative and discovery mechanics**: a narrated gallery of famous ants with milestone detection (the chaos→highway transition at ~10k steps), live-editable rule tables with instant restart, side-by-side comparison, stat overlays (steps, speed, entropy), deterministic seeds + shareable runs, and theming that makes screenshots beautiful. The science itself supplies the script — the ant's story is already dramatic.

### Cited Findings
**The narrative content is scientifically sourced and dramatic:**
- Langton's ant shows three phases: a few hundred steps of small symmetric patterns, then ~10,000 steps of irregular "chaotic" blob-building, then a sudden fall into a **104-step cycle** that moves the ant two squares diagonally forever, laying down 12 black cells per cycle — the "highway." One source counts the transition at step 9,976; another (arXiv) at iteration 10,100 — counts differ by counting convention; both agree on the ~10k magnitude. — [Matpic, "An ant that builds a highway"](https://www.matpic.com/essays/an-ant-that-builds-a-highway/), [Turmites are Turing-universal, arXiv:1702.05547](https://arxiv.org/html/1702.05547), [Gajardo/Moreira/Goles via ScienceDirect, "Complexity of Langton's ant"](https://www.sciencedirect.com/science/article/pii/S0166218X00003346)
- **Proven**: the ant's trajectory is unbounded from any finite starting configuration (Bunimovich & Troubetzkoy, 1992 — via a corner-avoidance argument on infinitely-visited cells). **Open**: the highway conjecture — that the ant eventually builds a highway from *any* finite start. — [Matpic](https://www.matpic.com/essays/an-ant-that-builds-a-highway/), [MathOverflow, "Intermediate results for Langton's ant highway conjecture" (2017)](https://mathoverflow.net/questions/277040/intermediate-results-for-langtons-ant-highway-conjecture)
- Experimental support is computable and displayable: of 60 random starting patterns tested, every one ended on a highway, with onsets ranging 553–42,175 steps (median ≈7,162); onset is unpredictable from the starting pattern's density. A simulator that surfaces these numbers is reproducing published research. — [Matpic](https://www.matpic.com/essays/an-ant-that-builds-a-highway/)
- **Universality**: the ant can simulate a universal Turing machine (via eventually-periodic infinite initial configurations, same standards as Rule 110's universality); prediction of its behavior from a large starting pattern is P-hard (evaluation of arbitrary Boolean circuits encodable as black-cell "wires and logic gates"). Consequently undecidable questions exist for infinite-support configurations. — [Gajardo, Moreira & Goles (2002), via dim.uchile.cl PDF](https://www.dim.uchile.cl/~anmoreir/oficial/langton_compx.pdf), [arXiv:1702.05547](https://arxiv.org/html/1702.05547), [cstheory.stackexchange discussion of the finite/infinite support distinction](https://cstheory.stackexchange.com/questions/14729/langtons-ant-highway-conjecture-and-undecidability)
- **Generalized turmites**: a 2017 result proves *every nontrivial turmite* (any rule where turn direction depends on the symbol) is Turing-universal, and predicting them is P-complete via a log-space reduction from the Topological Circuit Value Problem. Langton's ant is the RLRL rule. — [arXiv:1702.05547](https://arxiv.org/html/1702.05547)
- Geometry matters: on hexagonal grids trajectories can be bounded (Wang's comparison across grids), and on graphs of degree ≥5 dynamics collapse to tree-shaped reachable zones — i.e., "grid topology" is a one-click exhibit that changes the math. — [Gajardo/Moreira/Goles PDF](https://www.dim.uchile.cl/~anmoreir/oficial/langton_compx.pdf)
- The ant was independently discovered by Greg Turk while experimenting with 2D Turing machines — hence "turmite" — and became "a popular subject of java applets, almost matching Conway's Game of Life," which is useful framing: the genre has nostalgia plus an open math problem. — [Gajardo/Moreira/Goles PDF](https://www.dim.uchile.cl/~anmoreir/oficial/langton_compx.pdf)
- Open problems a simulator can display live: Is the set of infinitely-visited cells always empty? Does the ant always turn finitely many times around the origin? Does it always build a highway? (The third implies the first two; all tested finite starts satisfy them.) — [carlosgmartin.com/ant](https://carlosgmartin.com/ant/index.html)
- The highway conjecture and Collatz are both Π⁰₂ statements ("for all inputs there exists a time at which the process halts") — a ready-made talking point connecting the project to mainstream CS folklore. — [MathOverflow answer](https://mathoverflow.net/questions/277040/intermediate-results-for-langtons-ant-highway-conjecture)

**Feature patterns that demonstrably earned attention in adjacent projects:**
- A "hardware synth" interface (Teenage Engineering OP-1-style rotary knobs and faders over a WebGL CA engine, with entropy and decay-trail controls) headlined a recent Show HN — distinctive art direction is itself a distribution strategy. — [HN: Cellular Automata Studio](https://news.ycombinator.com/item?id=46285882)
- Live parameter mutation + replay: Cellarium lets you change parameters while the simulation runs via a TUI, and pressing "s" saves the complete history (parameters changed at given ticks) to JSON so any discovery can be replayed and regenerated — directly transferable to a browser turmite (export the rule-tweak timeline as a shareable replay). — [HN: Cellarium](https://news.ycombinator.com/item?id=47096186)

### Inferences
- **A "famous ants" narrated gallery** is the single highest-leverage feature because both reference sites lack any narrative. Milestone detection (e.g., detect highway onset via drift-direction invariance of the trailing pattern, then freeze-frame and label "step 9,976: the ant starts building") converts raw simulation into a story reviewers remember.

- **Theming**: light/dark + 2–3 curated palettes (terminal-green, blueprint, Teenage-Engineering-warm); screenshots that look good are what actually travels on X/Reddit.

## What is the prioritized polish checklist (repo → demo → social → résumé)?

### Takeaway
Work in this order: (1) demo must never be broken and must show motion on first paint; (2) README with GIF + Mermaid diagram + benchmark numbers; (3) narrated gallery + permalinks as the differentiating features; (4) OG/social cards; (5) résumé bullets with measured numbers. Items 1–2 are table stakes reviewers check in the first 60 seconds; items 3–5 are what outflank langtonant.com and evolvecode.io.

### Inferences (checklist built from all cited findings above)

**Tier 0 — must be true before anything else ships:**
- [ ] Live demo URL works on mobile and desktop, loads <2s, and has an ant already moving on first paint (reviewer funnel: 10s homepage → 20s project; broken demo = worse than none). — DevPlaybook, Solid Web
- [ ] Every claim on the résumé/README is reproducible from the repo (tests green, seeds deterministic, benchmark script runs).

**Tier 1 — repo (the credibility layer):**
- [ ] README: logo/hero → one-sentence description → badge row (CI, tests, license, live demo) → **animated GIF demo** (Gifski/ScreenToGif; ≤10MB; drag-and-drop onto GitHub CDN) → one-command or one-click quickstart → Mermaid architecture diagram (engine / renderer / interaction / state-URL layers) → benchmark table (steps/sec vs grid size, with method) → TOC → link to live demo first line. — glamfire priorities, banger-readme audit, awesome-readme
- [ ] Meaningful commit history (no "wip"); ~200-commit story of iteration is itself a signal. — DevPlaybook, Solid Web
- [ ] Tests: unit tests for rule stepping, state serialization round-trips, milestone detector; CI badge green. — DevPlaybook
- [ ] Pinned on the GitHub profile; profile README mentions the project. — DevPlaybook #16/#18

**Tier 2 — demo page (the wow layer):**
