# Build a Turmite Simulator That Outclasses Rivals

Build Exios66/langtons-ant as a single TypeScript + Vite app running entirely on the main thread — a chunked typed-array world grid, a two-layer dirty-rect Canvas2D renderer, and a data-driven flat rule-table engine that spans the classic ant through full (state × color) turmites — deployed to GitHub Pages. The main thread is not a compromise: SharedArrayBuffer threading is undeployable on GitHub Pages without cross-origin-isolation headers, and one ant step costs only ~14 ns of JavaScript, leaving roughly 700,000 steps of headroom inside every 10 ms frame budget ([chirs/cellular_automata](https://github.com/chirs/cellular_automata), [web.dev: COOP & COEP](https://web.dev/articles/coop-coep)). Critically, the engine is not where this project wins. langtonant.com, the first reference, is a 2017-frozen demo with no play/pause/step controls, reset-on-every-change, and randomly colored presets ([langtonant.com](https://langtonant.com/)); evolvecode.io/turmites, the stronger reference, still ships no sharing, no export, no telemetry, no touch input, and raw-JSON rule entry ([evolvecode.io/turmites](https://evolvecode.io/turmites/index.html)). Across thirteen surveyed competitors, the same five features are unclaimed: live-editable visual rule tables, seeded shareable permalinks, measured telemetry with highway detection, touch parity, and media export — so combining evolvecode's rule depth, dwmkerr's sharing model, and Golly's data-driven rigor, then adding those five, wins the category by construction. The ant's own science supplies the narrative for free: the 9,977-step chaos→highway transition, two universality theorems, and the open Highway Conjecture — with 2024–2025 proven highway families making the gallery content citably current ([Gajardo–Lutfalla–Rao 2024](https://arxiv.org/abs/2409.10124)). Expect roughly six to eight part-time weeks from empty repo to launch, with a working deployed ant by the end of week one.

## One flat rule table spans LR ants to full turmites — if you dodge the chirality traps

The classic ant is the 2-color, 1-state *relative* turmite: at each step it reads the color of the cell beneath it, turns 90° (right on white, left on black in Wikipedia's canonical wording), flips that cell's color, and advances one cell in the new heading ([Wikipedia: Langton's ant](https://en.wikipedia.org/wiki/Langton%27s_ant)). From a blank grid it runs three phases — a few hundred steps of simple symmetry, then pseudo-random "chaos," then at step **9,977** (the GollyGang Rule Table Repository's count) it locks into a **104-step periodic highway** that displaces it 2 cells diagonally per period, laying 12 black cells per cycle ([GollyGang wiki](https://github.com/GollyGang/ruletablerepository/wiki/TwoDimensionalTuringMachines), [Wikipedia](https://en.wikipedia.org/wiki/Langton%27s_ant)). That milestone number is convention-dependent, and this is the first trap: MathWorld's figures show the highway fully formed by ~10,647 steps, a 2025 arXiv note counts the onset at iteration 10,100, and the widely-circulated Matpic essay says 9,976 — the same event, counted differently ([MathWorld](https://mathworld.wolfram.com/LangtonsAnt.html), [arXiv:1702.05547](https://arxiv.org/html/1702.05547), [Matpic](https://www.matpic.com/essays/an-ant-that-builds-a-highway/)). The simulator should therefore *self-measure* highway onset and display the measured value, using 9,977 as the documented reference figure for the blank-grid RL preset — and let the CI golden-hash test (Section 5) pin the exact trajectory.

The general engine is one abstraction up: a turmite is a Turing machine whose tape is a 2-D grid and whose head additionally carries an orientation, with a per-(state, color) action of the form *(write color, turn by a multiple of 90°, next state, move/halt)* ([Wikipedia: Turmite](https://en.wikipedia.org/wiki/Turmite)). **Relative** turmites turn L (90° left), R (90° right), N (no turn), or U (180°) relative to their heading and are rotation-isotropic — Langton's ant is one; **absolute** turmites make compass moves (N/S/E/W) and are literally 2-D Turing machines. Turmites are exactly as powerful as 1-D Turing machines, proven rigorously in 2017 for *every nontrivial turmite* ([arXiv:1702.05547](https://arxiv.org/abs/1702.05547)). The rule-space size sets the scope of any "explore" mode: a relative square machine with M states and N colors over {L, R, N, U} has (4·N·M)^(M·N) labeled tables — 16⁴ = **65,536 raw tables for 2-state 2-color** (fully enumerable in the browser) versus 24⁶ ≈ **191 million for 2s3c** (needs a search strategy like GollyGang's [terminatingturmites](https://github.com/gollygang/terminatingturmites)) ([GollyGang wiki](https://github.com/GollyGang/ruletablerepository/wiki/TwoDimensionalTuringMachines)).

The importer should accept the four encodings that dominate the community. First, **L/R turn strings** for generalized ants: one letter per color, cell color cycling +1 on each visit, with the Gale–Propp base-2 numbering (L→1, R→0) indexing the literature — ant 2 = LR, ant 9 = LRRL, ant 12 = LLRR, ant 98 = LLRRRLR ([Gale–Propp–Sutherland–Troubetzkoy 1995](https://ar5iv.labs.arxiv.org/html/math/9501233)). Second, **GollyGang triple tables** `{{{1,2,0},{0,8,0}}}`: one {write, turn, nextState} triple per (state, color), with square-grid turn codes 1 = forward, 2 = right, 4 = U-turn, 8 = left, 0 = halt — and the codes are *additive*, so 10 = left+right splits one ant into two; this is the lossless interchange format of the entire Rule Table Repository and every busy-beaver record on it ([GollyGang wiki](https://github.com/GollyGang/ruletablerepository/wiki/TwoDimensionalTuringMachines)). Third, **Wikipedia-Commons decimal IDs** — state-major triple concatenations such as `111180121010`, which decodes to a spiral-growing 2s2c turmite ([Wikipedia: Turmite](https://en.wikipedia.org/wiki/Turmite)). Fourth, **Golly's compact L/R/U/N rule names** like `RRLLLRLLLRRR` ([Wikipedia](https://en.wikipedia.org/wiki/Langton%27s_ant)) — with a documented caveat: the exact pair-ordering of Golly's in-app Turmites shorthand could not be verified from any online source during research, so verify it inside the Golly app before shipping that importer ([GollyGang wiki](https://github.com/GollyGang/ruletablerepository/wiki/TwoDimensionalTuringMachines)). Hexagonal grids extend the turn alphabet to N/R1/R2/U/L1/L2 (60° steps), worth supporting as a topology flag ([Wikipedia](https://en.wikipedia.org/wiki/Langton%27s_ant)).

The second trap cluster is **preset fidelity**. Wikipedia words the canonical rule as right-on-white; MathWorld words it right-on-black — chiral mirrors that produce mirrored, not different, dynamics ([MathWorld](https://mathworld.wolfram.com/LangtonsAnt.html)); Gale–Propp write the classic ant as `LR` while Wikipedia names it `RL`, the same ant up to which color is "state 1" ([Gale–Propp 1995](https://ar5iv.labs.arxiv.org/html/math/9501233)). A gallery assembled naively from multiple sources will mix mirror images. The fix is to pin one convention app-wide — GollyGang's "color 0 → turn right," encoded as `{{{1,2,0},{0,8,0}}}` — document it in the README and the UI's rule panel, and normalize imported ant-strings to the leading-L canonical form, which halves the preset space and matches the community census of 57 canonical L/R rules ([A Bestiary of Turmites](https://williamhackspeare.github.io/turmite-bestiary)). Two further traps: the Esolang formulation ("invert the cell, step, then turn by the cell now ahead") is the same system with the turn shifted one step, so it yields identical trajectories but off-by-one step counts ([Esolang: Langton's ant](https://esolangs.org/wiki/Langton%27s_ant)); and additive turn codes spawn multiple ants whose annihilation breaks the system's reversibility, so undo/backward-stepping must be gated when extinction rules are active ([GollyGang wiki](https://github.com/GollyGang/ruletablerepository/wiki/TwoDimensionalTuringMachines)). Finally, torus mode changes the asymptotics outright — a finite state space plus reversibility forces eventual periodicity, and the published symmetry proofs explicitly fail on the torus — so the UI should warn when wrapping is enabled ([Gale–Propp 1995](https://ar5iv.labs.arxiv.org/html/math/9501233)).

## Thirteen competitors leave sharing, teaching, and telemetry unclaimed

The two references set the bar low in different ways. **langtonant.com** is a vanilla-JS demo whose source repo (coder369/langtons-ant, 18 stars) has been frozen since July 2017; it has *no play/pause/step/reset controls at all* — the sim auto-starts and every option change destroys progress with a full reset — custom rules accept only the letters L and R, preset colors are generated randomly rather than curated, there is no viewport meta tag (so no mobile layout), no zoom/pan, no URL state, and a data-entry bug where the dropdown option labeled "100" actually steps 10 times per refresh ([langtonant.com](https://langtonant.com/), [source JS](https://langtonant.com/js/moore-sof.langton-ant.min.js), [repo](https://github.com/coder369/langtons-ant)). Its one virtue is respectable raw scale: an `Int8Array` grid up to 5000×5000. **evolvecode.io/turmites** (~MaxRobinsonTheGreat/turmites, 11 stars) is the real baseline to beat: a genuine multi-state/multi-color machine with 8 move kinds (relative L/R/N/U/S, absolute ^>v<, random ?), 12 well-curated presets including Busy Beavers and a 15-step "Smiley Face" drawing program, 1–1024 ants with optional per-ant random rules, cursor-anchored zoom/pan with dirty-cell rendering, and a 1–100,000 steps/sec slider with catch-up scheduling ([evolvecode.io/turmites](https://evolvecode.io/turmites/index.html), [script.js](https://evolvecode.io/turmites/script.js), [presets.js](https://evolvecode.io/turmites/presets.js), [repo](https://github.com/MaxRobinsonTheGreat/turmites)). But the entire script audit confirms: no step-once button, no step counter, no measured steps/sec, no URL state, no image/GIF export, no localStorage, no touch handlers, no highway detection, no accessibility, ~60 console.log calls in production, and a rule editor that asks users to hand-edit JSON inside a `contenteditable` `<pre>`.

The rest of the field splits into three clusters with no overlap. The **one serious sharing app** is dwmkerr/langtonsant (30 stars, active 2026): a formal transformation-tuple rule DSL with an npm-published compiler, `?p=` URL sharing, and a six-example gallery with screenshots and deep links — but ant-only, no multi-state turmites, no zoom, no export ([README](https://raw.githubusercontent.com/dwmkerr/langtonsant/master/README.md), [demo](https://dwmkerr.github.io/langtonsant/)). The **feature gold standard** is the Golly ecosystem — desktop 5.0 (Oct 2025), iPad and Android apps, and a browser port of Golly 4.3 with RuleLoader user rules, unbounded grids, hashlife, and unlimited undo — but it is Life-first, desktop-parity UI that overwhelms rather than teaches ([Golly](https://golly.sourceforge.io/), [Golly web app](https://golly.sourceforge.io/webapp/golly.html)). The **modern toys** each carry one good idea and no depth: neuroky.me ships FPS + mobile-friendliness + help overlay ([neuroky.me/turmites2.html](https://neuroky.me/turmites2.html)); Jmakesthingswith/antfarm (Dec 2025) has undo/redo, a stats overlay, and an importable JSON example gallery ([repo](https://github.com/Jmakesthingswith/antfarm-simulator)); t3rmit3 advertises save/load/share of rule configs ([repo](https://github.com/screenseva/t3rmit3)); mdciotti and mysimulator.uk are single-feature demos ([mdciotti](https://mdciotti.github.io/turmites/), [mysimulator.uk](https://www.mysimulator.uk/langtons-ant/)). The desktop world shows what's possible and what's missing on the web: cenonym/trmt (85 stars, Rust CLI) runs 256 heads over ~10¹⁵ random rules with deterministic seeds ([repo](https://github.com/cenonym/trmt)); rrwick/Langtons-Ant-Animator exports supersampled animation frames ([repo](https://github.com/rrwick/Langtons-Ant-Animator)); and MrCamoga/Langton-s-Ant runs a *distributed* highway-discovery cluster computing period, size, and rotation — the only highway-detection implementation found anywhere, and it is desktop-only Java ([repo](https://github.com/MrCamoga/Langton-s-Ant)). Performance ceilings are owned by GPU/hashlife outsiders: glife3's WebGL2 engine claims ~1000× CPU speed ([glife3](https://glife3.org)) and copy.sh/life runs patterns with trillions of cells in-browser ([copy.sh/life](http://copy.sh/life/)).

The audit's conclusion is structural: every surveyed competitor implements at most 2–3 items from the checklist {full rule editing, sharing, export, touch, stats, documentation}, and **no web turmite app has image/GIF/video export, touch-optimized interaction, measured steps/sec telemetry, highway detection, or in-app rule-space education** ([audit of 13 implementations](https://langtonant.com/)). ## Chunked typed arrays, dirty rects, and one thread: the engine blueprint

### Grid storage and the memory math

Use a **paged/chunked grid**: `Map<number, Uint8Array>` where each chunk is a 64×64 (4,096-cell, 4 KB) `Uint8Array` keyed by a packed chunk coordinate — `(cx & 0xFFFF) << 16 | (cy & 0xFFFF)` — with chunk-local indexing `(y & 63) << 6 | (x & 63)`, lazy chunk creation, and the last-referenced chunk cached (a moving ant stays in the same chunk ~99% of consecutive steps, so the hot path is one Map hit per few thousand steps) ([Golly, production precedent for tiled unbounded universes](https://golly.sourceforge.io/), [nluka/langant-explorer, 1 byte/cell state format](https://github.com/nluka/langant-explorer)). The memory math decides the design outright. Each ant step touches exactly one cell, so after 10⁸ single-ant steps the chunked grid costs **≤ 100–200 MB** (1 byte/cell plus ~24k–49k Map entries of chunk index) — trivially inside a browser tab's budget. A sparse `Map<packedXY, color>` costs an estimated 40–80 bytes per entry (a V8 hash-table estimate that should be validated with Chrome DevTools snapshots before being quoted publicly), so the same workload lands at **4–8 GB: infeasible**. A colony of 10⁵ ants × 10⁴ steps = 10⁹ step-events pushes the chunked design to ~1 GB worst case (still viable with lazy chunks and an eviction cap) versus 40–80 GB for the sparse Map (impossible). Rule of thumb: chunked typed arrays stay viable to ~10⁸–10⁹ live cells; a sparse Map caps out near 10⁶–10⁷. A fixed torus (e.g. 8192² = 64 MB) is constant-memory but wrong for the flagship demo — a 10⁸-step highway is ~10⁸ cells long and wraps an 8192-wide torus ~12,000 times, running the ant over its own road and destroying the iconic unbounded growth; keep the torus as an opt-in "screensaver" mode with a warning that it changes the asymptotics. Eviction is optional and semantically delicate: for Langton's ant, monotonically growing memory *is* the correct behavior, since the pattern is permanent.

### Rendering: a two-layer dirty-rect Canvas2D pipeline

Layer one is an offscreen "world texture" canvas at 1 cell = 1 pixel, updated incrementally via `putImageData` with its dirty-rectangle argument so only the cells changed this frame are painted; layer two is the visible canvas, repainted each frame with a single `drawImage(worldTexture, …)` under a pan/zoom context transform with `imageSmoothingEnabled = false` ([MDN: putImageData](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/putImageData)). The measured numbers dictate every choice: full-frame `putImageData` of a 320×180 buffer costs ~50 µs, extrapolating to milliseconds for a 4K-sized buffer — enough to eat a 60 fps budget if done every frame ([MeasureThat: clearing canvas](https://www.measurethat.net/Benchmarks/Show/33628/1/clearing-canvas-v2)); canvas-to-canvas `drawImage` blits are ~2 orders of magnitude cheaper than pixel round-trips (~1.15M ops/s vs ~16K ops/s) ([MeasureThat: putImageData vs drawImage](https://www.measurethat.net/Benchmarks/Show/589377)); and per-pixel `fillRect` is 30–100× slower than batched ImageData writes — the single worst renderer choice for this workload, and exactly what the older reference does ([MeasureThat: fillRect vs putImageData](https://www.measurethat.net/Benchmarks/Show/33591/1/drawing-pixels-putimagedata-vs-fillrect), [langtonant.com JS](https://langtonant.com/js/moore-sof.langton-ant.min.js)). The dirty-rect payoff is extreme for this simulation specifically: **one ant changes exactly one cell per step**, so steady-state rendering cost is ~0 versus ~2 ms full-frame. Switch to a full-frame recomposition of the viewport (decompose only chunks intersecting the visible rect into one reused ImageData) when changed cells exceed ~5% of viewport pixels, as in multi-ant chaos. Set `canvas.width = cssWidth * devicePixelRatio` capped at DPR 2 to halve fill rate, keep `worldX = (screenX − panX) / zoom` with zoom-at-cursor anchoring, and for zoom-out below 1 px/cell switch to per-chunk thumbnail downscaling — the same minification tiering Golly ships for extreme zoom-out ([Golly Help: QuickLife](https://golly.sourceforge.io/Help/Algorithms/QuickLife.html)). WebGL2 (one grid texture + palette-LUT fragment shader) only wins at ≥4K viewports with heavy overlays; keep it as a stretch goal, matching the roadmap posture of existing JS CA engines ([chirs/cellular_automata](https://github.com/chirs/cellular_automata)). OffscreenCanvas-in-Worker is the escalation if profiles ever show raster jank — it is Baseline since March 2023 with ~96.8% support and `transferControlToOffscreen()` lets the worker own the canvas outright ([MDN: OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas), [caniuse](https://caniuse.com/offscreencanvas)).

### Scheduling: an adaptive rAF budget, log-slider, and turbo

The step itself is nearly free — a measured production JS engine does ~73M cell-updates/s ≈ 14 ns/cell, and one ant step is comparable work, so 1M steps/s consumes under 2% of a frame ([chirs/cellular_automata](https://github.com/chirs/cellular_automata)). Time actually goes to rasterization and GC: per-frame allocation is the documented silent killer in JS CA sims, so the step loop must be allocation-free and the ImageData reused, never reallocated per frame ([Teb's Lab: Optimizing Conway's Game of Life](https://medium.com/tebs-lab/optimizing-conways-game-of-life-12f1b7f2f54c)). Schedule with `requestAnimationFrame` and an adaptive steps-per-frame controller targeting a ~10 ms budget: measure `dt` per frame; if `dt < 12 ms`, multiply the batch by 1.25 (capped at ~250K); if `dt > 17 ms`, shrink by `dt/16.7` — this self-tunes across hardware with no benchmark mode. Map the speed slider logarithmically, `stepsPerSec = 10^(lerp(0, 6, s))` over 1 → 1M steps/s, converting to per-frame batches with a remainder accumulator so slow speeds get exact integer steps (1 step/s really steps once per second). Turbo mode runs 10⁶–10⁷-step batches without touching the canvas, renders one frame every ~50 ms, and yields at least every 100 ms to keep input live; at 14 ns/step a one-shot "fast-forward 10⁸ steps" button costs ~1.4 s of pure compute and is acceptable with an explicit "may freeze ~2 s" affordance. **The threading verdict is decisive: skip SharedArrayBuffer entirely.** SAB requires `Cross-Origin-Opener-Policy: same-origin` plus `Cross-Origin-Embedder-Policy: require-corp` document headers ([web.dev: COOP & COEP](https://web.dev/articles/coop-coep)), and GitHub Pages serves static files with no custom response headers — an SAB build breaks the primary deployment target. The science agrees: ants are inherently sequential through shared grid state, so colony-scale parallelism would spend more on chunk-level locking contention than it saves. Ship the main-thread loop; optionally decouple rendering later via a plain Worker + `transferControlToOffscreen()` with postMessage, never SAB.

### Rule engine: flat transition tables, serialized as data

Make the engine data-driven over a flat table — presets are then pure data, and adding one requires zero engine changes. For generalized ants (N colors, 1 state), a `Uint8Array(N)` turn table with values L=0, R=1, N=2, U=3 gives a branch-free hot path: `c = grid[i]; grid[i] = (c+1) % N; dir = (dir + delta[turnTable[c]]) & 3;` — two array reads, one write, no allocation ([Luxembourg Turmites report, 3-matrix formalization](https://math.uni.lu/eml/assets/reports/2022/turmites.pdf)). For full turmites, pack each (state, color) entry as write|turn|nextState in a `Uint16Array` of size states×colors (or parallel `Uint8Array`s), indexed `state*colors + color`; encode halt as nextState −1 (evolvecode's convention) or turn code 0 (GollyGang's) and normalize on import. Accept a three-tier rule-string grammar: (1) `^[LRNU]+$` ant strings covering every Turk/Propp rule; (2) comma-separated turn/write/state tuple strings for M×N machines, human-editable in the visual matrix; (3) a base64-packed table mirroring Golly's MAP-rule precedent (a 512-bit Life table, 86 base64 chars) for shareable URLs and lossless import/export ([Golly Help: QuickLife MAP rules](https://golly.sourceforge.io/Help/Algorithms/QuickLife.html)). The importer normalizes all four community notations (Section 1) into this internal table, with the GollyGang triple format as the canonical lossless interchange. Strict layering makes it testable: `engine/` (grid, rule, stepper — pure, integer-only, allocation-free in `step`), `render/` (world texture + viewport compositor), `app/` (rAF loop, UI, URL encoding) — the engine module then imports cleanly into Node for tests, the same headless pattern chirs/cellular_automata ships ([chirs/cellular_automata](https://github.com/chirs/cellular_automata)).

### Persistence: hash permalinks, RLE files, seeded replay

Three persistence tiers. **URL hash** for shareable runs: `#r=<ruleString>&a=<packedAnts>&s=<steps>&g=<rleBase64url>` — rule in plain text, ants base64-packed as (x:i16, y:i16, dir:2bits) records, step count in base36, and the grid RLE-encoded only when the encoded size is small; keep total under ~2 KB (the only universally safe URL guarantee), with a "state too large for URL — copy to file instead" fallback ([chirs/cellular_automata ships exactly this Share-button pattern](https://github.com/chirs/cellular_automata)). The hash (not query params) is the right choice for GitHub Pages: it is never sent to the server, needs no config, and keeps the OG card URL stable. **File save/load** for full state: `{version, rule, colors, rngSeed, stepCount, ants:[{x, y, dir, state}], grid:{bbox, chunkRLE}}` — the complete sufficient state vector, matching the production JSON format of langant-explorer plus a version tag ([nluka/langant-explorer](https://github.com/nluka/langant-explorer)); also ship bare-bones RLE import/export for Golly/LifeWiki interop, since RLE is the ecosystem's lingua franca ([Golly](https://golly.sourceforge.io/)). **localStorage** for UI prefs and session autosave. Determinism comes free from pure integer math plus an app-seeded PRNG (mulberry32 or xoshiro128\*\*; `Math.random` is unseedable and must never feed the simulation), with the seed stored in the URL and every save. Because ants step sequentially rather than as a synchronous cellular automaton, the cross-engine iteration-order divergence that plagues Life replayers doesn't exist here — integer-only JS step code replays identically everywhere, and the golden-hash CI test (Section 5) pins that claim ([Langton's Ant field notebook](https://langton-ant-tau.vercel.app/)). A bonus falls out of the physics: the classic ant is reversible, so backward-stepping/scrub is nearly free for pure relative rules — implement "replay any run from rule + seed + poses + step count" as re-simulation at up to ~10⁸ steps/s, with checkpoints every 10⁶ steps if scrubbing feels sluggish ([Esolang: Langton's ant](https://esolangs.org/wiki/Langton%27s_ant)).

### Tests, CI, and the GitHub Pages deployment path

Layer the tests where each is cheap. **Vitest unit tests (Node, headless)**: the rule-string parser (accepts `RL`, rejects malformed input), table construction, `step()` on a 3×3 world with hand-computed outcomes, RLE/base64 round-trips, save/load round-trips, chunk-boundary crossings (ant stepping across a 64×64 chunk edge), and eviction/refcount logic — the same headless engine-test pattern the Rust/WASM Life tutorial and chirs/cellular_automata both ship ([chirs/cellular_automata](https://github.com/chirs/cellular_automata), [Rust and WebAssembly book: testing](https://rustwasm.github.io/book/game-of-life/testing.md)). **Property tests (fast-check)**: for random rules and starts — exactly one cell changes per single-ant step, |Δx|+|Δy| = 1, direction stays in [0,3] without `%` drift, cells touched stay within the K-step neighborhood, and serialize→deserialize→step ≡ step. **Golden-hash determinism**: run RL for 11,000 steps, hash the visited bounding box with FNV-1a, and compare against a committed constant on every Node version and OS in CI (details in Section 5). **Playwright smoke (Chromium-only project)**: load `dist/` via `vite preview`, dispatch fixed steps, assert `toHaveScreenshot` with `maxDiffPixelRatio` ~0.01 and `animations: 'disabled'`, and read the hash out of the live page via `page.evaluate(() => window.__sim.hash())` — keeping screenshots deterministic means Chromium-only and per-environment baselines, since Playwright explicitly warns snapshots vary by host OS and hardware ([Playwright: visual comparisons](https://playwright.dev/docs/test-snapshots)). CI is one test workflow (`npm ci` → `vitest run` → `tsc --noEmit` → `playwright test`) plus one deploy workflow: Vite with `base: '/langtons-ant/'`, repo Settings → Pages → Source: **GitHub Actions**, and the official `actions/upload-pages-artifact@v5` + `actions/deploy-pages@v5` jobs on push to main — no `gh-pages` branch, exactly the recipe Vite documents ([Vite: Deploying a Static Site](https://vite.dev/guide/static-deploy)).

## The repo proves, the page narrates, the gallery converts

Reviewers spend a ~60-second funnel per project — skim the profile (10 s), click one project (20 s), scan code (20 s) — and under 90 seconds on a whole GitHub profile, with ~71% of hiring managers weighing GitHub activity at all ([DevPlaybook](https://devplaybook.cc/blog/developer-portfolio-checklist-20-things-hiring-managers/), [Scalyz](https://blog.scalyz.com/en/portfolios-github-profiles-hiring)). The winning structure is a two-layer system. The **repo is the credibility layer**: hero banner → one-sentence description → badge row (CI, tests, license, live demo) → an **animated demo GIF immediately after the fold** (≤10 MB, drag-dropped onto GitHub's CDN; demo GIFs are the single biggest missed opportunity even among excellent repos) → one-click quickstart → a **Mermaid architecture diagram** of the engine/render/app layers → a benchmark table with its method stated → TOC and docs ([banger-readme audit](https://github.com/kerryhatcher/banger-readme/blob/main/docs/exemplary-readmes.md), [awesome-readme](https://github.com/matiassingers/awesome-readme)). Commit history is a reviewed signal — meaningful messages, no "wip" — and the engine's unit + property tests with a green CI badge answer the "zero tests" red flag directly ([DevPlaybook](https://devplaybook.cc/blog/developer-portfolio-checklist-20-things-hiring-managers/)). The **demo page is the narrative layer**, run as a Ciechanowski-style case study: open with a live, already-running ant and an explicit "click to disturb it"; ramp from the two-state rule to why ~10,000 steps of chaos precede the highway; narrate what to notice ("notice the symmetry break at step ~150"); openly state where the model simplifies; and anchor every section to a live control rather than a screenshot — the format that made Ciechanowski's articles HN mainstays and that neither reference site attempts ([learn-ui.com on explorable explanations](https://learn-ui.com/chapters/explaining/explorable-explanations), [mangodeveloper teardown](https://mangodeveloper.com/articles/bartosz-ciechanowskis-interactive-sound-article-is-the-best-physics-explainer-youll-play-with-all)).

The **narrated gallery with milestone detection** is the single highest-leverage differentiator because both references are control panels without a story. Each famous-ant card carries its rule string, a 2–3 sentence story, and a one-click permalink; the milestone detector — a windowed check on the ant's trailing path for periodicity-plus-drift, per Lutfalla's formal highway definition ([arXiv:2506.10482](https://arxiv.org/abs/2506.10482)) — freezes and labels the moment: "step 9,977: the ant starts building." The science hands you the content: of 60 random starting patterns tested in published experiments, every one ended on a highway with onsets ranging 553–42,175 steps (median ≈7,162) — a distribution the app can surface live ([Matpic](https://www.matpic.com/essays/an-ant-that-builds-a-highway/)). Stat overlays (steps, measured steps/sec, entropy, bounding-box growth) tie the visible chaos→order transition to numbers, and side-by-side comparison mode (two synchronized canvases, shared scrubber) makes the rule space visible at a glance — neither exists in any surveyed competitor ([stat-overlay precedent](https://neuroky.me/turmites2.html)). **Shareability** is mechanical and cheap: `og:title`/`og:description`/`og:image`/`og:url`/`og:type` plus `twitter:card="summary_large_image"` with absolute HTTPS URLs at 1200×630 (OG tags must be baked into the static HTML since Pages has no server logic), the repo social preview uploaded at 1280×640 showing a *real highway screenshot*, validation via the Facebook Sharing Debugger (platforms cache scrapes for days), and one-click PNG/WebM export so every user's screenshot advertises the project ([GitHub Docs: social preview](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/customizing-your-repositorys-social-media-preview), [DrinkBird OG guide](https://blog.drinkbird.com/courses/jekyll-engineering-blog-github-pages/04-production-polish/02-open-graph-and-social-previews/)). Throttled `history.replaceState` (~1/s) keeps the permalink current mid-run.

The **interview talking points** hang off decisions-with-rejected-alternatives, which is what interviewers remember ([LastRound AI](https://lastroundai.com/blog/side-projects-vs-gpa)). Each maps to a section above: why rules are data (URLs, replay, and comparison mode all fell out for free); why main-thread over SAB (deployment constraint + sequential physics); why dirty rects (one cell changes per step); why seeds (reproducibility = shareability + testability). The 20-second science pitch: *"Langton's ant is a universal 2D Turing machine — predicting it is P-hard ([Gajardo–Moreira–Goles 2002](https://arxiv.org/abs/nlin/0306022)); every nontrivial turmite is Turing-universal ([arXiv:1702.05547](https://arxiv.org/abs/1702.05547)); and whether it always builds its highway is an open conjecture of the same logical flavor as Collatz ([MathOverflow](https://mathoverflow.net/questions/277040/intermediate-results-for-langtons-ant-highway-conjecture)) — my simulator makes that conjecture something you can watch."* The 2024–2025 results sharpen it further: the L(2k)R ants provably build ≥ k−1 distinct "harmonic" highways and `LLRLRL` provably has infinitely many ([Gajardo–Lutfalla–Rao, *Natural Computing* 2025](https://link.springer.com/article/10.1007/s11047-025-10018-9)), while `LLRRRL` and `LLRLRLL` provably reach non-highway asymptotic behaviors too — so a generalized Highway Conjecture *fails*, sharpening how special the classic RL ant is ([Lutfalla 2025a](https://arxiv.org/abs/2505.05426)). Résumé bullets follow the action-verb + scope + measured-outcome formula with real numbers filled in from the build ([techinterview.org](https://www.techinterview.org/post/3233474604/quantifying-impact-engineering-resume/)): *"Built a zero-dependency browser simulator for 2D Turing machines rendering [N]M steps/sec at 60 fps via chunked typed arrays and dirty-rect Canvas2D — live at [URL]"*; *"Designed a data-driven rule engine where any turmite is a serialized table, enabling ~10¹⁵-rule seeded exploration and URL-encoded permalinks — every run reproducible from its link"*; *"Shipped a narrated gallery with automatic highway-milestone detection (chaos→highway at step 9,977) and [N] unit/property tests in CI."* Launch choreography: repo + live URL → Show HN with a concrete hook ("start with this permalinked rule at 50× speed and watch it find the highway") → GIF/clip on X with the OG card doing the work → portfolio case study linking both.

## Four milestones from empty repo to launch, pinned by an 11,000-step golden hash

The build order front-loads a working deployed ant and defers everything the references also lack. Effort estimates are judgment calls calibrated against the codebases audited (evolvecode's full feature set is ~1,750 lines of vanilla JS, the parity baseline for Tier 1); treat them as planning anchors, not commitments.

Total: **~6–8 part-time weeks**, MVP deployed in week one. The golden-grid determinism test deserves its own emphasis because it is the technical thesis of the whole project in one assertion: run the classic RL ant 11,000 steps from a blank grid — comfortably past the 9,977-step highway onset documented by the Rule Table Repository and consistent with the ~10,000–11,000 figures in the literature ([GollyGang wiki](https://github.com/GollyGang/ruletablerepository/wiki/TwoDimensionalTuringMachines), [Luxembourg EML report](https://math.uni.lu/eml/assets/reports/langton.pdf)) — then hash the visited bounding box in deterministic cell order with FNV-1a and commit the digest as a test constant. Any Node version, any CI OS, and the live Playwright-run page must all produce the identical digest. One test simultaneously pins integer determinism of the step function, correctness of the chunked-grid addressing, and integrity of the rule-table serialization — and because the highway's 104-step periodic tail is part of what the hash covers, any drift in any layer fails loudly. Highway-formation assertions ("highway intact by step N") are possible but fiddly; the hash is the robust formulation ([Playwright: visual comparisons](https://playwright.dev/docs/test-snapshots)).

## Conclusion

The counterintuitive takeaway from this research is that the simulator's value concentrates almost entirely *outside* the engine: the rule system is a flat table, the step function is 14 nanoseconds, and a competent week-one MVP matches the references' simulation depth — while every feature that makes the project memorable (seeded permalinks, milestone detection, export, the taught rule space) lives in the last four weeks. Build accordingly: over-invest in the gallery, the sharing plumbing, and the measurement layer, and resist the gravitational pull toward engine heroics like WebGL or hashlife that the deployment target and the workload don't reward. The second implication is that the open Highway Conjecture is not just a talking point but a content engine: because every run is deterministic, seeded, and permalinked, the app quietly becomes a small research instrument — each visitor's run is a reproducible data point in a distributed, informal highway-onset census, echoing what MrCamoga's distributed cluster and Matpic's 60-pattern study did by hand. That framing — "a toy that is also an instrument" — is the interview story, and the 2024–2025 proven highway families mean the gallery cites theorems younger than the repo itself. Very few portfolio projects can make either claim; this one gets both from the same design decision, determinism everywhere.
